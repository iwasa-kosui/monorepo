# テスト方針（iori）

テストは「壊れたら困る振る舞い」を守るために書く。実装をもう一度書き写しただけのテスト（1=1 の証明）は書かない。
テストを足すときは、そのテストが落ちたときに本番のどんな不具合を防いだことになるのかを一文で言えることを条件にする。

## 書かないテスト（全レイヤー共通）

- **写経テスト**: 定数・設定値・スキーマのキー一覧・列挙値・ルート一覧などを、実装と同じ値を並べて `toEqual` するもの
- **パススルーの確認**: モックが返した値がそのまま返ること、受け取った引数がそのままモックに渡ることだけを確かめるもの
- **呼び出しの確認だけ**: 結果や状態を見ず `toHaveBeenCalledWith` / 呼び出し順だけを検証するもの（外部への副作用そのものが仕様である場合を除く）
- **型・Zod が保証することの再確認**: 自明な brand 型の parse 成否、`orThrow` が投げること、必須フィールド欠落で失敗すること
- **マークアップの文言・CSS クラス・HTML 構造の存在確認**: `toContain('text-terracotta')` や見出し文言が出ることだけを見るもの
- **クエリビルダのモック**: Drizzle のメソッドチェーンを偽物で組み、行→ドメインの写像を確かめるもの（実 SQLite で確かめる）
- **配線・移行作業の名残**: 「ルートがマウントされている」「旧ルートが無くなった」「ファクトリが関数を返す」といった作業時点の確認
- **重複**: 下位レイヤーで検証済みの分岐を、上位レイヤーでもう一度すべて並べ直すもの

## レイヤーごとに価値のあるテスト

| レイヤー | 守るもの | 書き方 |
|---|---|---|
| `domain/` | 不変条件、状態遷移、ドメインイベントの生成、非自明な計算・正規化・パース | 純粋関数として入力→出力。境界値と不正入力を中心に |
| `useCase/` | 業務フローの分岐: 認可・所有者チェック、失敗時に副作用が起きないこと、冪等性、イベントの発行 | インメモリのアダプタで状態を観察する。モックの呼び出しではなく結果と保存状態を見る |
| `adaptor/d1`, `adaptor/pg` | SQL の振る舞い: 絞り込み、並び順、ページング、upsert・競合、削除の連鎖、JSON 列の往復 | `sqliteFixture` 等の実 DB に対して書き、読み戻して確かめる |
| `adaptor/routes` | HTTP 契約: 認証・認可（401/403）、入力検証（400/422）、Mastodon 互換クライアントが依存するレスポンス形状・ページングヘッダ | ルーター単位で、外部から見える契約だけを見る |
| `adaptor/fedify`, `bluesky`, `mastodon` 等の外部プロトコル | 外部表現⇔ドメインの非自明な変換、受信データの防御的な解釈、署名・ブロック等の安全性 | 実際のペイロードに近い入力で |
| `ui/` | 純粋ロジック（整形、URL 組み立て、状態遷移、フックの状態管理）、XSS 等の安全性 | 描画文言や CSS クラスは検証しない |
| `scripts/` | デプロイ・マイグレーションの安全性: 破壊的操作のガード、プロセス制御、失敗時の復旧 | コマンド文字列や設定ファイルの中身の写経はしない |
| `workerd-tests/` | 実ランタイムでしか分からない結合（D1・Workers の互換性） | 単体テストで十分なものはここに書かない |
