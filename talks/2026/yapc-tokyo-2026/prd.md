# セッションPRD: 自己破産から見出すプロジェクトマネジメントの真髄

## 1. 要求（Requirements）

本PRDは、YAPC::Tokyo 2026 に応募するプロポーザルを作る前段として、セッションの目的、聴衆、スコープ、成功条件を整理する。

### 1.1 主催者の要求

`report.md` の採択要件分析を踏まえると、YAPC::Tokyo 2026 の主催者は次の要求を持つと考えられる。

| 要求ID | 要求 | 優先度 |
| --- | --- | --- |
| R-H1 | **独自経験**: 登壇者本人にしか話せない一次経験に根差していること | 必須 |
| R-H2 | **パッチワーク性**: 家族の破産実務、プロジェクトマネジメント、プラットフォーム開発の知見を接続すること | 必須 |
| R-H3 | **技術者への持ち帰り**: 聴衆が自分の現場で使える判断軸、情報設計、ステークホルダーマネジメントの実践知を得られること | 必須 |
| R-H4 | **明瞭性**: タイトルと概要から、何をどこまで話すのか判断できること | 必須 |
| R-H5 | **倫理性**: 家族、法律、病気、破産というセンシティブな題材を、消費的・暴露的に扱わないこと | 必須 |
| R-H6 | **YAPC文脈**: Perlに閉じないが、YAPC参加者が関心を持ちやすい「異なるものをつなぐ実践」「長く続く現実への対処」として提示すること | 推奨 |

## 2. 概要

### セッション情報

| 項目 | 内容 |
| --- | --- |
| 仮タイトル | 自己破産から見出すプロジェクトマネジメントの真髄 |
| イベント | YAPC::Tokyo 2026 |
| 形式 | 20分トーク |
| 代替形式 | 40分トーク |
| 推奨カテゴリ | プロジェクトマネジメント、プラットフォーム開発、ステークホルダーマネジメント |
| 想定難易度 | 初級から中級 |

### 背景

2024年から2025年にかけて、父の事業が立ち行かなくなり、会社は倒産することになった。連帯保証していた父自身も自己破産することになったが、父はうつ病の悪化により、破産手続きのために必要な行動を単独で進めることが難しい状態だった。

この状況では、弁護士、破産管財人、債権者、親戚、家族など、多数のステークホルダーが関わった。それぞれのゴール、関心、守るべきルール、提出すべき書類は異なっていた。さらに、親戚を巻き込んだ遺産相続問題も重なり、多くの電話や確認が登壇者に集まった。

このとき役に立ったのが、普段の仕事で使っていたプロジェクトマネジメントの技術だった。ロードマップ管理、課題管理表、ステークホルダー一覧表を作ることで、弁護士や管財人とのやり取りが整理され、家族が次に何をすればよいかも明確になった。

### 目的

一見すると技術開発と無関係に見える破産手続きの実務に、プラットフォーム開発やプロジェクトマネジメントの知見がどう効いたのかを共有する。特に、ゴールが異なるステークホルダーの期待値を制御すること、必要十分な情報を相手の立場で伝えること、内部と外部のマイルストーンを分けて余白を作ることの重要性を伝える。

### キーメッセージ

> **ステークホルダーが多く、当事者が弱っている状況ほど、プロジェクトマネジメントは人を追い詰めるためではなく、約束を守れる小さな活動に分解するために使える。**

### YAPC::Tokyo 2026 との接続

YAPC::Tokyo 2026 のテーマ「パッチワーク」に対して、このセッションは次の文脈を縫い合わせる。

- 家族の破産手続きと、技術開発のプロジェクトマネジメント
- 法律実務のステークホルダーと、プラットフォーム開発のステークホルダー
- 個人の困難と、技術者が持つ情報整理・期待値調整の技術
- 最終ゴールを見据えた計画と、目の前の小さな行動

Perlに直接閉じた話ではないが、YAPC参加者に馴染みのある「異なるものをつなぐ」「長く続く現実に対処する」「やり方は一つではない」という文脈に接続できる。

## 4. スコープ（Scope）

### スコープ内（In Scope）

| カテゴリ | 内容 |
| --- | --- |
| 背景 | 父の事業の破綻、会社倒産、連帯保証による自己破産、うつ病悪化により本人だけでは手続きが進まなかった状況 |
| 複雑性 | 弁護士、破産管財人、債権者、親戚、家族など、ゴールが異なるステークホルダーが存在したこと |
| 方法論 | ロードマップ管理、課題管理表、ステークホルダー一覧表の使い方 |
| 情報設計 | 相手の立場・目線に合わせて必要十分な情報を伝えること |
| 期待値調整 | 情報を出しすぎると混乱が増え、出さなさすぎると信頼を失うというバランス |
| マイルストーン設計 | 父に課す内部マイルストーンと、弁護士・管財人などに対する外部マイルストーンを分けること |
| プラットフォーム開発との接続 | ステークホルダーのゴールが異なる横断プロジェクトとの類似性 |
| 持ち帰り | ステークホルダー一覧表、課題管理表、ロードマップを作る際の判断軸 |

### スコープ外（Out of Scope）

| カテゴリ | 理由 |
| --- | --- |
| 法的助言 | 破産、相続、連帯保証の一般的な法務解説は専門外であり、弁護士に相談すべき領域 |
| 医療・心理的助言 | うつ病への対応方法そのものは医療専門家の領域 |
| 家族の詳細な個人情報 | セッションの価値は暴露ではなく、実務知の抽象化にある |
| 破産手続きの時系列の完全再現 | 20分では焦点が散るため、プロジェクトマネジメント上の判断に関係する範囲に絞る |
| 「プロジェクトマネジメント万能論」 | 役に立った範囲と限界を明示する |
| プラットフォーム開発の技術詳細 | 主題は技術実装ではなく、ステークホルダーと情報の設計 |

| セクション | 時間 | 内容 |

| 導入 | 2分 | タイトル、話すこと・話さないこと、法的・医療的助言ではないことを明示 |

| プラットフォーム開発との接続 | 3分 | 相手の立場に合わせた情報設計、内部/外部マイルストーンの余白、約束を守る設計 |
| まとめ | 2分 | 最終ゴールを見据えて小さく活動する。PMは人を追い詰める道具ではなく、複雑性を下げる道具 |

### 代替アウトライン（40分）

40分で応募する場合は、20分版に次を追加する。

| 追加セクション | 時間 | 内容 |
| --- | ---: | --- |
| ステークホルダー分析の深掘り | 6分 | 弁護士、管財人、父、家族、親戚、債権者の関心とゴールの違い |
| 情報設計の失敗例 | 5分 | 情報を出しすぎた場合、出さなさすぎた場合に何が起きるか |

### 必須コンテンツ

#### 1. ステークホルダー一覧表の例

| ステークホルダー | ゴール | 関心 | 必要な情報 | 避けるべき情報過多 |
| --- | --- | --- | --- | --- |
| 父 | 手続きを完了し生活を立て直す | 次に何をすればよいか、期限、負担 | 今日やること、次の提出物、誰に何を渡すか | 法的論点の全体像、複数先の未確定事項 |
| 弁護士 | 手続きに必要な情報を揃える | 書類、期限、事実関係、連絡可能性 | 事実、未提出物、優先順位、連絡窓口 | 家族内の感情的な経緯 |
| 破産管財人 | 財産・債務・取引の確認 | 正確性、期限遵守、説明可能性 | 根拠資料、時系列、未確認事項 | 推測や感情的説明 |
| 親戚 | 相続や家族関係への不安を下げる | 自分への影響、今後の見通し | 確定事項、相談先、次の節目 | 手続きの細部、未確定の可能性 |

実際のセッションでは、実名・具体的金額・詳細な法的事実を除いた抽象例として示す。

#### 2. 課題管理表の役割

| 項目 | 意図 |
| --- | --- |
| 課題 | 何が未解決かを一文で書く |
| 担当 | 父、登壇者、弁護士、その他の誰が動くかを明確にする |
| 期限 | 外部期限と内部期限を分ける |
| 次の一手 | 弱っている当事者でも動ける粒度まで小さくする |
| ブロッカー | 書類不足、本人確認、親戚からの返答待ちなどを分離する |
| 連絡先 | どこへ聞けばよいかを迷わないようにする |

#### 3. ロードマップ設計の原則

- 対外的に約束する期限よりも、内部の完了目標を前に置く
- 父に依頼する作業は、まとめて渡さず、今日・今週の単位に分ける
- 未確定事項は未確定として扱い、推測で親戚や関係者に伝えない
- 最終ゴールを「破産手続きの完了」と置きつつ、毎回の行動は小さくする
- 専門家に任せるべき判断と、家族側で集めるべき情報を分ける

#### 4. プラットフォーム開発への翻訳

| 破産手続きでの学び | プラットフォーム開発での対応 |
| --- | --- |
| ステークホルダーごとにゴールが違う | 利用チーム、運用、セキュリティ、法務、経営の成功条件を分けて管理する |
| 情報を全部出すと混乱する | 相手の判断に必要な情報だけを渡す |
| 内部期限と外部期限を同じにすると破綻する | チーム内マイルストーンと対外ロードマップに余白を持たせる |
| 弱っている当事者に大きなタスクを渡すと動けない | チームや利用者の認知負荷を下げる粒度で依頼する |
| 約束を守ることが信頼を作る | スコープを小さくして予測可能性を上げる |

### オプショナルコンテンツ

- 実際に使った表の匿名化サンプル
- 家族支援における「やらないことリスト」
- 「必要十分な情報」を判断するためのチェックリスト
- プロポーザル用のタイトル比較

## 6. 制約条件

### 時間制約

- 応募締切: 2026年9月1日 23:59 JST
- セッション候補: 20分トークを第一候補とする
- 20分の場合、背景説明を広げすぎず、ステークホルダー管理とマイルストーン設計に絞る

### 表現上の制約

- 破産、連帯保証、うつ病、相続といった言葉を使う場合は、必要な範囲に限定する
- 父や親戚を「問題の原因」として描かない
- 当事者の弱さを笑い、驚き、ドラマとして消費しない
- 「自分が解決した」という語りではなく、「専門家と家族が動ける状態を作った」という語りにする
- 法的・医療的な一般化を避ける

### 守秘・倫理制約

- 実名、会社名、金額、住所、事件番号、具体的な債権者名は出さない
- 家族に共有して問題のない範囲で事例化する
- 実際の書類画像は使わない。使う場合は完全に再作成したダミーにする
- 感情的な電話や家族間のやり取りは、具体発言ではなく構造として説明する

## 7. リスクと対策

| リスク | 影響度 | 対策 |
| --- | --- | --- |
| 個人的な話に寄りすぎ、技術カンファレンスでの価値が見えない | 高 | 各セクションの最後に「プラットフォーム開発では何に相当するか」を置く |
| 法的助言に見える | 高 | 冒頭で法的助言ではないことを明示し、手続き論ではなく情報整理に絞る |
| 家族のセンシティブな情報を消費しているように見える | 高 | 個人情報を伏せ、尊厳を守る語りにする。話の主語を「管理」ではなく「動ける状態を作る」に置く |
| 20分に対して背景が重すぎる | 高 | 経緯説明は4分以内にし、詳細な時系列は扱わない |
| プラットフォーム開発との接続が後付けに見える | 中 | ステークホルダー、情報設計、内部/外部マイルストーンの対応表を中心に構成する |
| 「PMすれば何でも解決する」という主張に見える | 中 | PMの限界、専門家に任せる境界、家族関係の難しさを明示する |
| 聴衆が重く受け止めすぎ、持ち帰りが薄くなる | 中 | 最後に具体的なチェックリストと小さな実践を提示する |

### PRD上の問題と具体的な解決策

[SaaS企業のプラットフォームチームとして大切にしていること](https://kosui.me/posts/2026/05/31/important-for-platform-team)（ローカル本文: `apps/kosui-me/src/content/posts/2026-05-31-platform.mdx`）の「ゴールから逆算して小さくつくる」「変更の可逆性を大切にする」「ステークホルダーと対話し続けよう」という考え方を、プロポーザルと登壇内容のリスクヘッジへ反映する。

#### 問題1: 個人的な体験が強く、技術カンファレンスの価値がぼやける

**何が危険か**:

- 「大変だった家族の話」として受け取られ、YAPC参加者が自分の現場に持ち帰れる知見が見えなくなる
- 破産、うつ病、相続という強い題材に注意が集まり、プロジェクトマネジメントとプラットフォーム開発の話が薄くなる
- 採択側から見て、技術カンファレンスの20分枠に入れる必然性が弱く見える

**解決策**:

- セッションの主語を「父の破産」ではなく「ゴールが異なるステークホルダーを、必要十分な情報でつなぐ設計」に置く
- 体験談は背景説明に限定し、各具体例を必ず次の3点へ接続する
  - 作った成果物: ロードマップ、課題管理表、ステークホルダー一覧表
  - 下げた不確実性: 期限、担当、提出物、連絡先、未確定事項
  - プラットフォーム開発での対応物: 対外ロードマップ、利用チーム別期待値、公開I/Fの責務
- 20分版では、背景4分、方法論8分、プラットフォーム開発への翻訳5分、まとめ3分を上限にする
- プロポーザル概要の冒頭で、次のように価値を先に置く

```text
このトークは破産手続きそのものの解説ではありません。
複数の関係者が異なるゴールを持ち、当事者が十分に動けない状況で、
ロードマップ・課題管理・ステークホルダー一覧表がどのように機能したかを、
プラットフォーム開発のステークホルダーマネジメントに翻訳して話します。
```

#### 問題2: 「父を管理した話」に見えると倫理的に危うい

**何が危険か**:

- うつ病で動けない父を、プロジェクト管理の対象として扱ったように見える
- 当事者の弱さを、登壇者の有能さを示す材料にしているように見える
- 家族の尊厳を損なう印象を与える

**解決策**:

- 「管理した」「動かした」「コントロールした」という表現を避け、「動ける状態を作った」「認知負荷を下げた」「専門家へ接続した」と表現する
- 父に関する説明は「病状の詳細」ではなく「一度に大きなタスクを扱うことが難しい状態だった」というプロジェクト上の制約に留める
- 父に課すタスクは、成果物の粒度として次のように示す

| 悪い渡し方 | 良い渡し方 |
| --- | --- |
| 必要書類を全部集めておいて | 今日、通帳のある場所だけ確認する |
| 弁護士に説明しておいて | この3点だけメモして、私から弁護士に渡す |
| 親戚に連絡しておいて | 誰に連絡すべきかだけ一緒に確認する |

- セッション内で明示する原則を次の一文に固定する

```text
弱っている当事者に強い計画を押しつけるのではなく、
当事者が守れる約束の粒度まで計画を小さくする。
```

#### 問題3: 法的助言・医療助言に見える

**何が危険か**:

- 破産、連帯保証、相続、うつ病という語が並ぶため、手続きや病気への対処を一般化しているように見える
- 質疑応答で法律相談や家族問題相談に寄ってしまう
- 資料公開後に、文脈を離れて助言として引用される

**解決策**:

- プロポーザル、冒頭スライド、公開資料の3箇所にスコープ宣言を入れる

```text
本セッションは法的助言・医療助言ではありません。
破産や相続に関する判断は弁護士などの専門家に相談してください。
ここでは、家族側が専門家とやり取りするための情報整理と期待値調整に話を限定します。
```

- Q&Aの回答方針を事前に決める
  - 法的判断を問われたら「専門家に確認してください」と返す
  - 医療・家族関係の対応を問われたら「一般化できない」と返す
  - 答える範囲は「情報をどう整理したか」「誰に何を渡したか」「期限をどう分けたか」に限定する
- 公開資料では、実際の金額、会社名、地名、書類名の細部、事件番号、家族内発言を出さない

#### 問題4: プラットフォーム開発との接続が後付けに見える

**何が危険か**:

- 「家族の話を技術っぽく言い換えただけ」に見える
- プラットフォーム開発の記事で重視している、中長期視点、公開I/Fの不可逆性、ステークホルダー対話の要素が反映されない
- 聴衆が「自分のプラットフォームチームで何を変えるべきか」まで持ち帰れない

**解決策**:

- セッション内の対応関係を、次の3本に絞る

| 記事のプラットフォーム原則 | 破産手続きでの対応 | 聴衆への持ち帰り |
| --- | --- | --- |
| ゴールから逆算して小さくつくる | 最終ゴールを手続き完了に置き、今日やることまで分解する | 長期ロードマップから逆算しつつ、依頼は小さく可観測にする |
| 変更の可逆性を大切にする | 未確定事項を確定事項として伝えない | 一度公開した情報やI/Fは依存される前提で扱う |
| ステークホルダーと対話し続ける | 弁護士、管財人、親戚、家族ごとに必要な情報を変える | 関連度の高い相手から対話し、相手の関心に合わせて情報を出す |

- 「プラットフォーム開発に近い」と言うだけでなく、公開I/Fの不可逆性と、親戚・専門家へ一度伝えた情報が訂正しにくいことを対応づける
- ただし、法律実務とソフトウェアを完全に同一視しない。対応表の前に次の断りを置く

```text
これは破産手続きとプラットフォーム開発が同じだという主張ではありません。
共通しているのは、異なる目的を持つ関係者が、後から取り消しにくい情報や約束へ依存する点です。
```

#### 問題5: 「必要十分な情報」が抽象的で、実践に落ちない

**何が危険か**:

- 良いことを言っているが、現場で使う基準にならない
- 「情報を絞る」が隠蔽や不誠実に見える
- 相手の立場に合わせるという話が、単なるコミュニケーション論に見える

**解決策**:

- 必要十分な情報を、次のチェックリストとして定義する

| 観点 | 質問 |
| --- | --- |
| 判断可能性 | 相手はこの情報で次の判断や行動ができるか |
| 確定度 | 確定事項と未確定事項が分かれているか |
| 責任境界 | 誰が決めることか、誰が作業することかが分かれているか |
| 認知負荷 | 今すぐ読まなくてよい背景を混ぜていないか |
| 再伝播リスク | 相手が別の人へ転送しても誤解されにくいか |
| 訂正コスト | 間違っていた場合に訂正できるか |

- 「情報を絞る」ではなく「相手が次の行動を取れる形に整える」と表現する
- 重要な未確定事項は隠さず、未確定ラベルを付けて伝える

#### 問題6: 内部マイルストーンと対外マイルストーンの余白が、単なるバッファに見える

**何が危険か**:

- 見積もりに余裕を持たせよう、という一般論に見える
- 父や家族に対する進捗圧力を隠しているように見える
- プラットフォーム開発でのロードマップ設計へ転用しにくい

**解決策**:

- 余白を「遅れを隠すためのバッファ」ではなく「外部の約束を守るための責任境界」と定義する
- 内部マイルストーンには、当事者の体調、書類探索、親戚からの返答待ち、専門家確認の揺らぎを含める
- 対外マイルストーンには、確実に守れる節目だけを置く
- スライドでは次の図式で説明する

```text
内部計画: 今日の確認 -> 今週の提出準備 -> 専門家への確認 -> 不足分の再収集
対外約束: 期限までに必要資料を提出する

内部計画は細かく変えてよい。
対外約束は少なく、守れるものに絞る。
```

#### 問題7: 資料公開後に文脈が失われる

**何が危険か**:

- セッション中の慎重な補足が、スライド単体では伝わらない
- 強い言葉だけが引用され、法務・医療・家族問題への助言に見える
- 個人的な体験が独り歩きする

**解決策**:

- 公開資料の最初と最後に、スコープ宣言と専門家相談の案内を入れる
- 実例スライドには、必ず「匿名化した構造例」「実際の書類ではない」と明記する
- SNSで共有されやすいまとめスライドには、次の3点だけを載せる
  - 相手の判断に必要な情報だけを渡す
  - 内部計画と対外約束を分ける
  - 弱っている人に渡すタスクは小さくする
- 家族の状況そのものを要約したスライドを、単独で切り出される形にしない

## 8. プロポーザル設計

### 推奨タイトル案

1. 自己破産から見出すプロジェクトマネジメントの真髄
2. 自己破産とプラットフォーム開発
3. 自己破産とプロジェクトマネジメント
4. 父の自己破産を支えたロードマップ、課題管理、ステークホルダー一覧表
5. 家族の破産手続きで学んだ、プラットフォーム開発のステークホルダーマネジメント

第一候補は `自己破産から見出すプロジェクトマネジメントの真髄` とする。プロジェクトマネジメントを主題として明示しつつ、自己破産という一次経験の意外性がある。やや大きい表現なので、概要では「PM万能論」ではなく、複雑な状況で人を追い詰めず、約束を守れる状態を作るための情報設計として説明する。

### プロポーザル概要の必須要素

1. 2024年から2025年にかけて、父の会社倒産と自己破産を支援した一次経験
2. うつ病の悪化により、父が単独で手続きを進めることが難しかった状況
3. 弁護士、破産管財人、親戚、家族など、ゴールの異なるステークホルダーがいたこと
4. ロードマップ管理、課題管理表、ステークホルダー一覧表が役に立ったこと
5. プラットフォーム開発と同じく、相手の立場に合わせた必要十分な情報設計が重要だったこと
6. 内部マイルストーンと対外マイルストーンに余白を作ること
7. 最終ゴールを見据えながら、小さく活動することの価値
8. YAPCのテーマ「パッチワーク」との接続

### 採択に向けた差別化

| 観点 | 差別化内容 |
| --- | --- |
| 独自経験 | 会社倒産、自己破産、うつ病、相続問題が重なった家族支援の一次経験 |
| 技術者への価値 | プラットフォーム開発で使うステークホルダーマネジメントを、別領域で検証した話として聞ける |
| YAPC接続 | 異なる制度、人、専門家、家族、技術知をつなぐ「パッチワーク」 |
| 空白領域 | AI、OSS、IaC、言語処理系に寄らない、プロジェクトマネジメントと情報設計の実践知 |
| 持ち帰り | ステークホルダー一覧表、課題管理表、ロードマップ設計原則 |

## 9. 想定Q&A

### Q: これは法律の話ですか？

A: 法律の解説ではありません。破産手続きそのものの判断は弁護士や管財人の領域です。このセッションでは、家族側が必要な情報を揃え、期限を守り、関係者との期待値を調整するために、プロジェクトマネジメントの考え方をどう使ったかを話します。

### Q: なぜYAPCで話すのですか？

A: YAPC::Tokyo 2026 のテーマは「パッチワーク」です。この話は、家族の破産手続き、法律実務、プロジェクトマネジメント、プラットフォーム開発のステークホルダーマネジメントを縫い合わせる話です。Perlに閉じた技術解説ではありませんが、異なるものをつなぎ、現実の制約の中で動くものを作るという意味で、YAPC参加者に持ち帰れる価値があります。

### Q: プロジェクトマネジメントで家族の問題は解決できますか？

A: できることとできないことがあります。病気や法律判断、家族関係そのものをPMで解決することはできません。一方で、誰が何をいつまでにするのか、何が未確定なのか、誰にどの情報を伝えるのかを整理することで、動ける状態を作ることはできます。

### Q: プラットフォーム開発との類似点は何ですか？

A: ステークホルダーごとにゴールが違うこと、守るべきルールが多いこと、情報を出しすぎても出さなさすぎても混乱すること、内部の作業計画と外部への約束を分ける必要があることです。これは、利用チーム、運用、セキュリティ、法務、経営が関わるプラットフォーム開発に近い構造です。

### Q: 具体的に何を持ち帰れますか？

A: ステークホルダー一覧表の作り方、課題管理表で「次の一手」を小さくする方法、内部マイルストーンと対外マイルストーンを分ける考え方、相手の立場に合わせて必要十分な情報を伝える判断軸を持ち帰れます。
