# セッションPRD: もう他人ごとじゃないイベントソーシング: 社会を支えるプロダクトにあとから監査性を縫い込む

## 1. セッション定義

| 項目       | 内容                                                                                       |
| ---------- | ------------------------------------------------------------------------------------------ |
| イベント   | YAPC::Tokyo 2026                                                                           |
| 形式       | 40分ライブコーディング・ハンズオン                                                         |
| 対象レベル | イベントソーシング未経験から初級                                                           |
| 使用技術   | TypeScript、SQLite                                                                         |
| 主題       | イベントソーシングをすぐ導入できない既存CRUDで、重要な状態変化をイベントとして記録し始める |
| タイトル   | もう他人ごとじゃないイベントソーシング: 社会を支えるプロダクトにあとから監査性を縫い込む   |

タイトルは変更しません。本セッションでは、イベントを正本とするイベントソーシングの実装ではなく、その前に既存システムで始められるイベント記録を扱います。

## 2. 背景

「いつか、社会の礎になるようなプロダクトに関わりたい」。そう思っていても、一般的なWebアプリケーションの開発と比べて、そこで何が求められるのかは具体的に想像しづらいものです。

医療、教育、行政、福祉、金融など、人の暮らしを支えるプロダクトには、信頼性、セキュリティ、プライバシーなど多くの品質が求められます。その一つが、現在の状態が正しいだけでなく、「なぜこの状態になったのか」をあとから説明できることです。本セッションは、この説明可能性に焦点を当てます。

登壇者自身も、社会を支えるプロダクトに必要な品質を具体的に理解していたわけではありません。イベントソーシングについても、最初から強い思想で設計されたシステムだけが採用するものだと考えていました。その見方が変わったのは、医療SaaSの共通基盤で、現在値しか残っていない顧客データに向き合ったときです。

現在のユーザー、施設、端末、ライセンスは確認できます。しかし、誰が、いつ、なぜ変更したのかは残っていません。問い合わせや障害対応では、断片的なログと関係者の記憶から変更経緯を推測する必要がありました。

イベントソーシングでは、イベント列を正本とし、現在状態をイベントから導出します。既存システムをすぐにそこまで移行できない場合でも、業務上重要な状態変化をイベントとして記録することは始められます。本セッションは、その最初の実装と判断を扱います。

## 3. 解決する問題

社会を支えるプロダクトに必要な品質が漠然としており、説明可能性を設計や実装の問題として捉えられていない状態を変えます。現在値だけを保存するCRUDでは、たとえば次の問いに答えられません。

- ライセンス数を10から100へ変更したのは誰か
- 変更はいつ発生したか
- 何を根拠に変更したか
- 変更前の値は何だったか
- 同じ問い合わせが再び起きたとき、同じ説明を再現できるか

現在値テーブルだけを正本としたままでも、更新と同じトランザクションで業務上の出来事を保存すれば、記録を始めた時点から変更経緯を説明できます。

## 4. 用語と責任境界

| 設計                 | 正本               | 記録するもの                       | 本セッションでの扱い       |
| -------------------- | ------------------ | ---------------------------------- | -------------------------- |
| 監査ログ             | 現在値または別のDB | 操作、アクセス、テーブル差分       | 違いを説明する             |
| ドメインイベント記録 | 現在値テーブル     | 業務上起きた状態変化               | 実装する                   |
| イベントソーシング   | イベント列         | 状態を決定するすべての業務イベント | 定義と将来の判断だけを扱う |

イベントを記録しただけの設計を、イベントソーシングとは呼びません。本セッションではこの違いを明示し、現在値テーブルを正本として残します。

## 5. 目的

参加者がセッション後に次の判断と実装をできる状態を目指します。

- 社会を支えるプロダクトでは、変更経緯を説明できることも品質の一つだと理解できる
- 監査ログ、ドメインイベント記録、イベントソーシングの違いを説明できる
- 業務上の状態変化をイベントとして命名できる
- 現在値の更新とイベント保存を同じトランザクションで実装できる
- イベント履歴から、誰が、いつ、なぜ変更したかを確認できる
- 記録開始前の過去を復元できないことを説明できる
- イベント記録で十分な領域と、イベントソーシングを検討すべき領域を分けられる

## 6. 中心となる主張

> 社会を支えるプロダクトでは、現在値を正しく保つだけでなく、そこへ至った変更を説明できることも品質になります。イベントソーシングを今すぐ採用できなくても、重要な状態変化をイベントとして残すことは今日からできます。

イベント記録は、社会を支えるプロダクトに必要な品質のすべてを解決するものではありません。しかし、変更理由の説明が信頼に直結する領域では、重要な出来事を失わない設計が具体的な一歩になります。その記録は説明可能性を高め、将来イベントソーシングへ移行するか判断する材料にもなります。

## 7. 想定聴衆

### 主対象: 社会を支えるプロダクトに関心があるアプリケーション開発者

医療、教育、行政、福祉、金融などのプロダクトにいつか関わりたいと考えています。一方で、機能を作ること以外にどのような品質が求められるのかは、まだ具体的に分かっていません。社会を支えるとは技術や設計にどう現れるのか、その一例をコードとともに知りたいと考えています。

### 副対象: CRUDを中心に開発してきたアプリケーション開発者

イベントソーシングという言葉は知っていますが、導入規模の大きさから自分のシステムには適用できないと感じています。現在の構成を維持したまま始められる実践を知りたいと考えています。

### 副対象: 問い合わせや監査対応を担当する開発者

現在値と断片的なログしか残っておらず、変更経緯の調査に時間を使っています。一般的な操作ログではなく、業務上の出来事として何を残すべきか判断したいと考えています。

### 副対象: 長期運用されるプロダクトの技術リード

将来の説明責任を考えて履歴を残したい一方で、既存システム全体のイベントソーシング化は現実的ではないと考えています。どこから始め、どの条件で次の設計を検討するか知りたいと考えています。

## 8. 題材

架空のライセンス管理を題材にします。開始時点では、ライセンスの現在値だけを保存するテーブルがあります。

| 項目               | 内容                                                                                         |
| ------------------ | -------------------------------------------------------------------------------------------- |
| 現在値テーブル     | プラン、席数、状態、最終更新日時                                                             |
| 変更イベント       | LicensePlanChanged、LicenseSeatLimitChanged、LicenseSuspended、LicenseReactivated            |
| イベントの共通項目 | イベントID、対象ID、イベント種別、発生日時、実行者、変更理由、スキーマバージョン、業務データ |
| 解決したい問い     | 誰が、いつ、なぜプランや席数を変更したか                                                     |

現在値テーブルが正本です。イベントには業務上の出来事を過去形で記録し、汎用的なUpdatedやテーブル差分だけで済ませません。

実在する顧客、施設、患者、契約のデータは使いません。医療SaaSで経験した問題構造だけを、架空のライセンス管理へ置き換えます。

## 9. ハンズオンの到達点

参加者は完成済みのスターターコードから始め、次の順に一つのCRUDを変更します。

1. 現在値しかないCRUDで、変更理由を説明できないことを確認する
2. LicenseSeatLimitChangedを業務イベントとして定義する
3. 更新前の値、更新後の値、実行者、変更理由をイベントへ含める
4. SQLiteの一つのトランザクションで現在値更新とイベント保存を行う
5. イベント保存に失敗した場合、現在値更新もロールバックされることを確認する
6. イベント履歴を時系列で取得し、変更経緯を説明する
7. この設計がイベントソーシングではない理由を確認する
8. イベントを正本へ変更すべき条件と、現在値を正本のまま維持する条件を整理する

参加者は手元でコードを実行しても、ライブコーディングを見るだけでも内容を追える構成にします。環境構築や定型コードの入力に時間を使わないよう、依存関係とテーブル定義は事前に用意します。

## 10. 40分の構成

| 時間     | 内容                                                           |
| -------- | -------------------------------------------------------------- |
| 0〜6分   | 社会を支えるプロダクトで求められる品質と、説明できなかった問い |
| 6〜11分  | 監査ログ、ドメインイベント記録、イベントソーシングの違い       |
| 11〜16分 | ライセンスCRUDと記録すべき業務イベントの設計                   |
| 16〜27分 | 現在値更新とイベント保存を一つのトランザクションへ入れる実装   |
| 27〜32分 | 保存したイベントから変更経緯を確認する実装                     |
| 32〜35分 | 失敗時のロールバックと、記録開始前の過去を扱えない限界         |
| 35〜40分 | イベント記録で十分な条件と、イベントソーシングを検討する条件   |

## 11. スコープ

### 扱うこと

- 一つのライセンスCRUDに対するイベント設計
- 追記専用のイベント記録テーブル
- 現在値更新とイベント保存のトランザクション
- 実行者、変更理由、変更前後の値の記録
- イベント履歴の照会
- 監査ログ、ドメインイベント記録、イベントソーシングの使い分け
- 記録開始後の変更に対する説明可能性

### 扱わないこと

- イベントを正本とする実装
- イベント列からの状態再構築
- 現在値プロジェクションの生成や再生成
- 既存データを初期イベントへ変換する移行
- イベントストア製品やフレームワークの比較
- Kafkaなどのメッセージ基盤
- 複数サービスをまたぐ分散トランザクション
- 記録開始前の変更理由を推測してイベント化すること
- 医療情報や患者情報の具体例

## 12. 技術上の制約

### イベントソーシングと呼ばない

現在値テーブルが正本である限り、この実装はイベントソーシングではありません。タイトルだけで完成形の実装を期待させないよう、プロポーザルの前半で扱う範囲を明記します。

### 更新と記録を同じトランザクションへ入れる

現在値更新に成功してイベント保存に失敗すると、変更経緯を説明できません。SQLiteの同一トランザクションで両方を確定し、片方だけ成功する状態を作りません。

### 業務上の出来事を記録する

テーブル名と更新操作だけを残すのではなく、LicenseSeatLimitChangedのように業務上何が起きたかを記録します。実行者と変更理由は、説明責任が必要な変更では欠落させません。

### 失われた過去を作らない

記録開始前の変更理由や順序は不明のままです。現在値から過去のイベントを推測して作りません。

### 機密情報をイベントへ複製しない

イベントは追記後に変更しないため、個人情報や不要な機密情報を業務データへ含めません。実演では架空データだけを使います。

## 13. リスクと対策

| リスク                                           | 対策                                                                         |
| ------------------------------------------------ | ---------------------------------------------------------------------------- |
| タイトルからイベントソーシングの実装を期待される | 冒頭で定義と実装範囲を示し、イベント記録との違いを明言する                   |
| 監査ログを追加するだけの話に見える               | テーブル差分ではなく、業務上の出来事を命名して記録する                       |
| 現在値とイベントが食い違う                       | 同一DBの一つのトランザクションで両方を保存する                               |
| イベントを残せば将来必ず移行できると誤解される   | イベントの網羅性と正本の変更は別の判断であり、自動的な移行ではないと説明する |
| 記録開始前の過去も説明できると誤解される         | 記録開始前の履歴は不明と明示する                                             |
| 医療事例の守秘範囲が曖昧になる                   | 実データや固有の業務フローを使わず、架空のライセンス管理へ置き換える         |
| イベント記録だけが必要な品質だと受け取られる     | 数ある品質のうち説明可能性に焦点を当てるセッションだと冒頭で明言する         |
| ライブコーディングが止まる                       | 節目ごとのディレクトリを用意し、途中状態から再開できるようにする             |

## 14. YAPC::Tokyo 2026との接続

YAPC::Tokyo 2026のテーマ「パッチワーク」に対し、既存CRUD、現在値テーブル、ドメインイベント、問い合わせ対応、監査要求を接続します。完成された新規システムではなく、すでに動いている仕組みへイベント記録を加える話です。

Perlを主題にはしませんが、現実の制約下で動くものを作り、複数の方法から適切な方法を選ぶというYAPC参加者の関心へつなげます。

## 15. 応募文の構成

応募文は1,000字以内を目安とし、次の順にします。

1. 社会を支えるプロダクトに関わりたいが、そこで何が求められるのか分からないという問い
2. そこで必要な品質の一つが、現在の状態に至った経緯を説明できること
3. 登壇者自身も具体的に理解していなかったこと
4. 医療SaaSで現在値しか残らないデータに向き合い、見方が変わった経験
5. イベントソーシングをすぐ導入できなくても、イベント記録は始められるという主張
6. 既存CRUDへイベント記録を追加するライブコーディング
7. イベント記録でできることと、イベントソーシングとの境界
8. イベント記録を、社会を支える開発を考える具体的な入口にしたいという意志

特定のイベント名、挙手の人数、知人の発言は応募文から外します。「聞いたことはあるが、自分たちには関係ないと思われがち」という一般化した状況だけを置き、第三者が特定される情報を使いません。

## 16. 採択前の成功条件

- タイトルの「もう他人ごとじゃない」に対応する認識の変化が本文で分かる
- 社会を支えるプロダクトに関心はあるが、必要な品質をまだ具体化できていない人が自分向けの発表だと分かる
- イベント記録は必要な品質の一例であり、すべてを解決するものではないと分かる
- 登壇者がイベントを記録する重要性を広めたい理由と意志が一人称で伝わる
- 特定のイベントや知人を識別できる情報が含まれていない
- イベント記録とイベントソーシングを同一視していない
- 現在値テーブルを正本として残すことが分かる
- 40分で何を実装するか判断できる
- 記録開始前の過去は復元できないと明記されている
- YAPC::Tokyo 2026のテーマとの接続が一文で分かる
