# セッションPRD: 「誰が、いつ、なぜ変えた？」に答えられないCRUDを、イベントソーシングで作り直す

## 1. セッション定義

| 項目       | 内容                                                                           |
| ---------- | ------------------------------------------------------------------------------ |
| イベント   | YAPC::Tokyo 2026                                                               |
| 形式       | 40分ライブコーディング・ハンズオン                                             |
| 対象レベル | イベントソーシング未経験から初級                                               |
| 使用技術   | TypeScript、SQLite                                                             |
| 主題       | 現在値しか残らない既存CRUDを、イベントを正本とする設計へ段階的に移行する       |
| 仮タイトル | 「誰が、いつ、なぜ変えた？」に答えられないCRUDを、イベントソーシングで作り直す |

本セッションは、イベントソーシングを社会を支えるプロダクトの監査性と説明可能性へつなげます。

## 2. 背景

医療SaaSの共通基盤を作る中で、現在値しか保存されていない顧客データに何度も向き合いました。ユーザー、施設、端末、ライセンスの値は確認できますが、誰が、いつ、なぜ変更したのかは残っていません。問い合わせや障害対応では、ログや関係者の記憶から変更経緯を推測する必要がありました。

イベントソーシングを知った当初は、最初から専用基盤を用意し、すべての状態をイベントから再構築する大規模な設計だと考えていました。そのため、既存のCRUDシステムには適用できないと思っていました。

本セッションでは、既存CRUDからイベントソーシングへ移行する具体的な手順を示します。一つの既存CRUDを題材に、移行時点の現在値を初期イベントとして取り込み、その後の変更をイベントとして保存し、イベント列から現在値を再構築します。失われた過去を復元できるとは主張せず、移行した時点から説明可能な履歴を作る方法を扱います。

## 3. 解決する問題

現在値だけを保存するCRUDでは、次の問いに答えられません。

- ライセンス数を10から100へ変更したのは誰か
- 変更はいつ発生したか
- 何を根拠に変更したか
- 変更前の状態は何だったか
- 特定時点の状態を再現できるか
- 現在値が壊れたときに再構築できるか

監査ログを別途書くだけでは、状態更新に成功してログ保存に失敗する可能性が残ります。本セッションでは、状態変更そのものをイベントとして確定し、そのイベント列を正本とします。現在値テーブルはイベントから作り直せるプロジェクションとして扱います。

## 4. 目的

参加者がセッション後に次の判断と実装をできる状態を目指します。

- 監査ログ、ドメインイベント、イベントソーシングの違いを説明できる
- 業務上の状態変化をイベントとして命名できる
- イベント列から集約の現在状態を再構築できる
- 楽観的並行制御を使ってイベントを追記できる
- イベントから現在値のプロジェクションを作れる
- 既存データを初期イベントとして取り込む際の限界を説明できる
- イベントソーシングを採用しない方がよい領域を判断できる

## 5. 中心となる主張

現在値だけでは、プロダクトに起きた変化を説明できません。イベントを正本にすると、現在の状態だけでなく、そこへ至った変更と理由を残せます。

イベントソーシングは、すべてのシステムへ適用する設計ではありません。一方で、医療、教育、行政、福祉、金融など、変更経緯の説明が信頼に直結する領域では、開発者が検討できる選択肢にする必要があります。

## 6. 想定聴衆

### CRUDを中心に開発してきたアプリケーション開発者

イベントソーシングという言葉は知っていますが、自分の既存システムへ適用する手順を想像できていません。イベントストアやCQRSの説明から始まる記事を読み、導入規模の大きさに不安を感じています。

### 問い合わせや監査対応を担当する開発者

現在値と断片的なログしか残っておらず、変更経緯の調査に時間を使っています。監査ログを増やすだけで十分なのか、状態変更の設計から見直すべきか判断したいと考えています。

### 長期運用されるプロダクトの技術リード

将来の説明責任を考えて履歴を残したい一方で、既存データの過去を復元できないことや、チームの運用負荷を懸念しています。段階的な導入範囲と撤退条件を知りたいと考えています。

## 7. 題材

架空のライセンス管理を題材にします。開始時点では、ライセンスの現在値だけを保存するテーブルがあります。

| 項目             | 内容                                                                              |
| ---------------- | --------------------------------------------------------------------------------- |
| 集約             | License                                                                           |
| 現在値           | プラン、席数、状態、最終更新日時                                                  |
| 解決したい問い   | 誰が、いつ、なぜプランや席数を変更したか                                          |
| 初期イベント     | LicenseImported                                                                   |
| 変更イベント     | LicensePlanChanged、LicenseSeatLimitChanged、LicenseSuspended、LicenseReactivated |
| プロジェクション | 現在のライセンス状態を参照するテーブル                                            |

イベントには、イベントID、集約ID、イベント種別、発生日時、実行者、変更理由、バージョン、業務データを保存します。実行者や変更理由をすべてのイベントに機械的に要求するのではなく、説明責任が必要な変更では欠落させない設計にします。

実在する顧客、施設、患者、契約のデータは使いません。医療SaaSで経験した問題構造だけを、架空のライセンス管理へ置き換えます。

## 8. ハンズオンの到達点

参加者は完成済みのスターターコードから始め、次の順に一つのシステムを変更します。

1. 現在値しかないCRUDで、変更理由を説明できないことを確認する
2. 状態変化をドメインイベントとして定義する
3. 現在値をLicenseImportedとして取り込む
4. 期待バージョンを指定してイベントを追記する
5. イベント列を畳み込み、ライセンスの現在状態を再構築する
6. イベントから現在値テーブルを更新する
7. 現在値テーブルを削除し、イベント列から作り直す
8. 特定時点までのイベントを再生し、当時の状態を確認する

参加者は手元でコードを実行しても、ライブコーディングを見るだけでも内容を追える構成にします。環境構築や定型コードの入力に時間を使わないよう、依存関係とテーブル定義は事前に用意します。

## 9. 40分の構成

|     時間 | 内容                                                             |
| -------: | ---------------------------------------------------------------- |
|   0〜5分 | 医療SaaSで現在値しか残っていなかった経験と、答えられなかった問い |
|   5〜9分 | 監査ログ、ドメインイベント、イベントソーシングの違い             |
|  9〜15分 | ライセンスCRUDとイベントの設計                                   |
| 15〜23分 | イベントストアへの追記と楽観的並行制御                           |
| 23〜29分 | イベント列から現在状態を再構築する実装                           |
| 29〜34分 | プロジェクションの更新と再生成                                   |
| 34〜37分 | LicenseImportedによる移行と、復元できない過去の扱い              |
| 37〜40分 | 採用条件、採用しない条件、持ち帰り                               |

## 10. スコープ

### 扱うこと

- 一つの集約に対するイベント設計
- 追記専用のイベントストア
- 集約の再構築
- 楽観的並行制御
- 現在値プロジェクション
- 既存データの初期イベント化
- 特定時点の状態再現
- 採用判断と運用上の注意点

### 扱わないこと

- イベントストア製品やフレームワークの比較
- 複数サービスをまたぐ分散トランザクション
- Kafkaなどのメッセージ基盤の構築
- CQRS全般の体系的な解説
- GDPRなどにおける削除要件の詳細
- 失われた過去の変更理由を推測してイベント化すること
- すべてのテーブルをイベントソーシングへ移行すること
- 医療情報や患者情報の具体例

## 11. 技術上の制約

### イベントを正本にする

現在値を更新した後に監査用イベントを書くだけの設計は、イベントソーシングとは呼びません。コマンドの結果としてイベントを追記し、そのイベントから現在状態を導出します。

### 失われた過去を作らない

LicenseImportedは、移行時点で確認できた現在値を記録します。それ以前の変更理由や順序を復元したものではありません。プロポーザルとセッションの両方で、この限界を明示します。

### 一つの集約に絞る

ユーザー、施設、端末、外部同期、監査ログを同時に扱うと、40分では実装と判断のどちらも浅くなります。題材はライセンス集約だけに限定し、他のパターンは採用判断の説明で触れるに留めます。

### ローカルで完結させる

TypeScriptとSQLiteを使い、外部サービスやクラウドアカウントを不要にします。イベント追記とプロジェクション更新はSQLiteのトランザクション内で実装します。非同期プロジェクションやOutboxパターンは、発展的な論点として名前だけ紹介します。

## 12. リスクと対策

| リスク                                     | 対策                                                                       |
| ------------------------------------------ | -------------------------------------------------------------------------- |
| 監査ログを追加する話に見える               | イベント列が正本であり、現在値を削除して再生成できるところまで実演する     |
| 既存システムの過去も復元できると誤解される | LicenseImportedより前の履歴は不明と明示する                                |
| 40分で実装が終わらない                     | 一つの集約へ絞り、スターターコードと完成版を用意する                       |
| イベントソーシング万能論に見える           | 現在値だけで十分な領域と、変更経緯が価値を持つ領域を比較する               |
| 医療事例の守秘範囲が曖昧になる             | 実データや固有の業務フローを使わず、架空のライセンス管理へ置き換える       |
| ライブコーディングが止まる                 | 節目ごとのタグまたはディレクトリを用意し、途中状態から再開できるようにする |

## 13. YAPC::Tokyo 2026との接続

YAPC::Tokyo 2026のテーマ「パッチワーク」に対し、既存CRUD、イベントストア、現在値プロジェクション、問い合わせ対応、監査要求を段階的に接続します。完成された新規システムではなく、すでに動いている仕組みへ新しい設計を加える話です。

Perlを主題にはしませんが、現実の制約下で動くものを作り、複数の方法から適切な方法を選ぶというYAPC参加者の関心へつなげます。

## 14. YAPC::Fukuoka 2025から取り入れる構成

YAPC::Fukuoka 2025の採択プロポーザルを確認すると、短い本文の中で一次経験、話したい理由、当日の内容を直接伝える例が目立ちます。

- [大規模OSSに一人で立ち向かうには](https://fortee.jp/yapc-fukuoka-2025/proposal/0d4c761a-df5b-46b9-83ef-66bea4f87fa3): 一人で取り組んだ経験と到達点を冒頭で示しています
- [Quine for Everyone](https://fortee.jp/yapc-fukuoka-2025/proposal/28b3a042-a2e9-4866-bd76-3be08608c7b2): 難しそうという不安を打ち消し、その場で一緒に書こうと誘っています
- [ecspressoの「正しい抽象化」の探求](https://fortee.jp/yapc-fukuoka-2025/proposal/0b964339-fb1d-463a-a99f-74b91f108e44): 8年間の開発経験、具体例、今回話す範囲を数段落で伝えています
- [「バイブス静的解析」でレガシーコードを分析・改善しよう](https://fortee.jp/yapc-fukuoka-2025/proposal/c4e33dea-0860-488d-ae37-db45c5c4acda): 課題、独自の呼び名、実装方針、到達点を短い段落と箇条書きで示しています

この傾向を踏まえ、応募文は次の順にします。

1. 実際に答えられなかった問い
2. 医療SaaSでの一次経験
3. ライブコーディングで作るもの
4. 移行でできることと、できないこと
5. イベントソーシングを広めたい理由

背景となる社会の変化、複数の既存データパターン、対象聴衆の長い列挙は応募文から外します。本文は1,000字以内を目安とし、主張を弱めない範囲で削ります。

## 15. 採択前の成功条件

- タイトルだけで、既存CRUD、イベントソーシング、解決したい問いが分かる
- 冒頭で登壇者の一次経験が伝わる
- イベントを記録するだけではなく、イベントを正本とすることが伝わる
- 40分で何を実装するか判断できる
- 既存データの失われた過去は復元できないと明記されている
- イベントソーシングを採用しない領域にも触れている
- YAPC::Tokyo 2026のテーマとの接続が一文で分かる
