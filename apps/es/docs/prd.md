# 「もう他人ごとじゃないイベントソーシング」製品要求書

状態: 講師が承認しました。決定の一覧は[講師が決めること](#講師が決めること)にあります。

このハンズオンの中心の対象者は、イベントソーシングの意味があまり分からないのにコストが高い選択肢だと思っている開発者です。参加者は、全体を移行しなくても必要なエッセンスを部分適用できることを、既存の更新処理で確かめます。参加者の認識が「既存プロジェクトには非現実的」から「部分的かつ意義のある活用ができる」へ変わることを目指します。

## 問題

プロポーザルの概要は、「医療・金融・教育など、社会を支えるプロダクトには、障害や問い合わせ、監査に対して「なぜ現在の状態になったのか」を説明できる品質が必要です。」と述べます。現在の状態だけを持つテーブルは、この問いに答えられません。

同じ概要は、「イベントソーシングはそのために有用ですが、「最初からイベント中心に設計しなければ使えない」「考えることが多く、現実的ではない」と思われがちです。」と続けます。講師もそう考えていました。講師は、問い合わせ、障害、監査の対応で過去を説明できず苦しみ、必要なエッセンスを既存システムへ部分適用するようになりました。

この問題を抱える開発者でも、語を聞いた時点で自分には関係ないと判断する可能性があります（仮説）。題名はこの語を出します。説明を語から始めると、最も参加してほしい人が困りごとを確かめる前に離れます（仮説）。

## 対象者

対象者の中心は、イベントソーシングの意味があまり分からないのに、コストが高い選択肢だと思っている開発者です（合意済み）。

プロポーザルの対象者は「イベントソーシングを何となく知っているが既存システムへの導入は現実的でないと感じている人」と「社会を支えるプロダクトの開発に興味がある人」です。この人たちも引き続き対象です。資料の入口は中心の対象者に合わせ、内容はプロポーザルの約束どおりにします。

対象レベルは初級から中級です。前提知識は、SQL の UPDATE と INSERT が読めることです。TypeScript は読めれば十分です。

## 目標

参加者が、終了時に次の4つを自分のシステムの言葉で言えることを目標にします。

1. 「この問いには、今のテーブルでは答えられない」
2. 「全体を移行しなくても、更新処理の境界に記録を足せば、足した後の変更を説明できる」
3. 「費用はこの程度で済む。足す前の過去は分からず、記録の漏れも残る」
4. 「3パターンのうち、自分のシステムに近いのはこれだ。何を活用し、何を記録しないかはこれだ」

目標1は「意味があまり分からない」に、目標3は「コストが高い」に答えます。プロポーザルの届けたいことと目標は、次のように対応します。

| 説明可能性を高められる           | 目標1、目標2 |

## 講師が決めること

### 題名の「イベントソーシング」

状態: 合意済み。

決定: 題名を変えません。導入で「他人ごと」の意味を講師の話として説明します。導入の一文で、イベントソーシングの考え方を段階的に適用できると伝えます。事前案内と告知に、中心の対象者にこそ来てほしいという趣旨の一文を足します。

### 本文の「イベントソーシング」

状態: 合意済み。

決定: 本文で使うのは、導入で疑いを受け止める文、導入で講師の考えを述べる文、導入で今日借りる考え方を示す文、導入で障害対応の体験の後に置くイベントソーシングとCQRSを説明するページ、導入で敬遠される理由を図で示すページ、まとめだけにします。まとめで、今日足したものがどのエッセンスで、何を足していないかを説明します。

理由: いまの資料には肯定形の定義がありません。参加者は、記録を足した後なら説明を自分の体験と比べられます。

### 「業務イベント」と「ドメインイベント」

状態: 合意済み。

決定: 第2章までは「記録」と書きます。第2章で「業務イベント」を一文で定義し、以降はこの語を使います。「ドメインイベント」は、まとめで関連記事を案内する一文だけに使います。

理由: 「業務イベント」はプロポーザルの語で、「ドメインイベント」はプロポーザルにありません。関連記事を読む人には語の対応を示す必要があります。

### テーブル名 `domain_events` と列名 `aggregate_*`

状態: 実装済み。

決定: 平易な名前に変えます。新しい名前は、この決定の後に講師と決めます。

理由: 第2章の穴埋めの4空欄のうち3つが `aggregate_*` です。参加者は9分の演習中に、語の意味を問わず書くことになります。費用は小さくありません。コミット `2a149ae0` の時点で、`domain_events` は追跡対象の37ファイル107行に、`aggregate_` は33ファイル97行に出ます。この行の多くは演習のスナップショットです。件数は教材の作り直しで変わります。関連記事のテーブル設計とは名前がずれるので、まとめの関連記事の案内に対応を一文で書きます。

別案は名前を残して意味だけ説明することです。費用は小さく済みますが、要求4を第2章で満たせません。

実装: テーブル名は `business_events`、列名は `target_id`、`target_type`、`target_state` に変えました。第2章のステップ2の空欄は `event_name`、`payload`、`target_type` の3つです。いまの教材の本文と演習のコードには、`domain_events` と `aggregate_` は出ません。この2つの語が出るのは、まとめの関連記事の案内と、この文書と、語の出現位置を検査するテストだけです。

### 第2章の演習の組み立て

状態: 実装済み。文面は講師の確認待ちです。

決定: 第2章の演習を2段にします。ステップ1は、問い合わせの「誰が」「いつ」「なぜ」に答える列だけを持つ `visit_cancellations` テーブルに、キャンセルの記録を追記します。ステップ1の後の ADR で、出来事ごとにテーブルを作るとテーブルが増えることを示し、記録を1つのテーブルにまとめます。「業務イベント」の定義と `business_events` の列は、この ADR で初めて出します。ステップ2は、ステップ1の `INSERT` を `business_events` 用に書き換えます。

理由: 講師の指摘は「いきなり「記録の列」が出てきてその通りに実装させられるのは納得感がない。最終的にこの形に自然となるように、問題の設計をゼロベースで見直して。」です。関連記事のテーブル設計の節は、出来事ごとにテーブルを定義する形を先に示し、数が増えるので一つのテーブルにまとめると述べています。SRE Kaigi 2026 の発表も、集約やイベントごとに分割したテーブルを単一テーブルに寄せた経緯を述べています。演習の順序をこの経緯に合わせました。要求4の「必要になった後に出す」にも合います。

### 第2章の説明の文書と図

状態: 実装済み。文面は講師の確認待ちです。

決定: 第2章の説明の2ページを、状況、決定、結果、検討した案の4節からなる ADR にします。状況の節には、判断の基準を書きます。決定の節には、決定の理由と、優先したことを書きます。結果の節には、採用した案の負担と制約も書きます。検討した案の節は、採用しなかった案ごとに、利点と採用しなかった理由を、見出しと段落で書きます。表にするのは、採用した案と採用しなかった案を同じ基準で比べる対応だけです。文面は、tanteki スキルの ADR の検査を通します。図は、ボタンを押さずに読める図にします。

理由: 講師の指摘は「設計メモよりも軽量なADR風の方がいいかな？ただそのADRはすごくわかりやすい図解付き、だと良い」と「「設計メモ: 更新処理の中で記録する」の図は意図は動かせばわかるけど最初はどう使えばいいのか分からず戸惑った」です。代替案の節を足した理由は、講師の指摘「もっとちゃんと背景や検討された代替案も書かれているべき」と「教材だからこそ真剣に他の選択肢のメリットにも言及した上でちゃんと棄却したい」です。代替案の表を見出しと段落に変え、採用した案を同じ基準の表に入れた理由は、講師の指摘「ADRと呼ぶにはメリットデメリットが公平に比較されていないし、表である必要がないものまで表になっていて読みづらい」です。

実装:

- 1ページ目の図は、上から、呼び出し元、`cancelVisit` の `withTransaction` の中の2つの書き込み、記録に成功する場合と失敗する場合の結果を並べます。呼び出し元が渡す `reason` と `operatedBy` と、`visit_cancellations` の行に入る値を、同じ色で示します。
- 3ページ目の図は、上の段で、出来事ごとのテーブルを1つのテーブルにまとめることを示します。下の段で、ステップ1の列が `business_events` のどの列に移るかを矢印で示し、各列を残す理由を添えます。

- 1ページ目の検討した案の表は、採用した案を含む6つの案を、状況の3つの基準で比べます。セルには○、△、×だけを入れ、理由は表の外に書きます。3ページ目の3つの案は、それぞれ決定の別の部分を変える案なので、表にしません。
- 1280x640 と 1440x790 の画面で、図の全体が文書の表示域に収まります。e2e で検査します。
- 第3章4ページ目の図は、「次へ」で時間を進める形のままです。

### 「足さない」の扱い

状態: 合意済み。

決定: 判断表に独立した選択肢として足しません。判断表には「何を部分的に活用し、何を記録しないか」の行を足します。主な成功は、認識の変化と、3パターンから適用方法を選べることです。自分の問いが無ければ足さなくてよいことは、まとめに一文で書きます。

理由: プロポーザルの約束は、どう適用するかを選ぶことです。この形なら第4章の時間をほとんど使いません。

### 導入の構成

状態: 実装済み。文面は講師の確認待ちです。

決定: 導入を7ページから8ページに組み替えます。1ページ目は、講師の近況から始めてつかみにします。イベントソーシングとCQRSの説明と図は、2ページ目の障害対応の体験の後に置きます。敬遠される理由は、この説明と同じ図で示します。「コードを見ない開発と品質の保証」のページは、講師の記事「ソフトウェアファクトリーとコード設計と顧客価値」の文で肉付けします。この記事は 2026-11-15 に公開されました。導入の時間を8分から10分に延ばします。

理由: 講師は 2026-11-27 に、導入の1ページ目と2ページ目について「P1の話はつかみとして弱い」「P1に対してP2が唐突すぎる」と指摘しました。P1 と P2 は、旧構成の1ページ目と2ページ目です。この指摘を受けて、1ページ目を講師の近況から始め、最後の文で2ページ目の障害対応の体験を予告します。説明のページを障害対応の体験の後に置くので、参加者が用語の説明を読む前に困りごとを確かめるという要求2と矛盾しません。講師は同じ日に、説明の不足を「ちょっとハイコンテクストだね。CQRSとかイベントソーシングの説明が全くない。具体的にどんな部分がそう見えるのか掘り下げて、それを図でわかりやすく説明してほしい。」と指摘しました。この指摘を受けて、説明のページと、敬遠される理由を示すページを足しました。「コードを見ない開発と品質の保証」のページについては、講師が同じ日に「ここもうちょい解像度が高い方がいいな」と指摘しました。導入の時間については、講師が同じ日に「導入の時間を延ばす」「もう1-2分ぐらい?」と回答しました。

- 4ページ目: イベントソーシングとCQRSを説明します。2ページ目のポチのキャンセルを題材にした図を置きます。
- 5ページ目: 4ページ目と同じ図に番号を付け、「最初からイベント中心に設計しなければ使えない」「考えることが多く、現実的ではない」と見られる箇所を示します。続けて、講師の当時の考えと経験を述べます。
