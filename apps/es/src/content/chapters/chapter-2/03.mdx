## 記録を1つのテーブルにまとめる

### 状況

この ADR の対象は、動物病院向けの予約システムです。予約システムのリポジトリは `clinic/clinic-api` です。

予約システムは、来院を `visits` テーブルで管理しています。

ADR 1 は、キャンセルした人と理由を後から回答できるように、来院のキャンセルの記録を `visit_cancellations` テーブルに保存する方式を定めています。`visit_cancellations` テーブルは、キャンセルのたびに1行を追記するテーブルです。連番の ID（`id`）、来院の ID（`visit_id`）、キャンセルした人（`operated_by`）、理由（`reason`）、日時（`cancelled_at`）の列を持ちます。来院のキャンセルの処理（`cancelVisit`）は、`visits` テーブルの更新と同じトランザクションで、`visit_cancellations` テーブルに記録を追記します。

`visit_cancellations` テーブルは、テーブルの名前と列の両方が、キャンセルの記録だけを対象にしています。診察の完了の処理（`completeVisit`）にも同じ方式で記録を追加すると、診察の完了を記録するテーブルがもう1つ必要になります。記録する出来事の数が増えると、テーブルの数も増えます。

出来事ごとにテーブルを分割した場合の運用負荷は、次の発表が報告しています。

<Quote source="SRE Kaigi 2026 の発表より">

また、最初は集約やイベントごとにテーブルを分割していましたが、運用負荷が高かったため、必要になるまでは単一テーブルに寄せるようにしました。過剰な設計を避けるという判断です。

</Quote>

この ADR は、出来事の記録を保存するテーブルの構成を決定します。

### 決定

出来事の記録を、1つのテーブルにまとめて保存します。

業務イベントは、業務で起きた1つの出来事を、「誰が」「いつ」「何を」「なぜ」とともに残す記録です。現時点で記録する業務イベントは、来院のキャンセルの1種類だけです。

業務イベントを保存するテーブルは `business_events` です。`visit_cancellations` テーブルの列は、`business_events` テーブルの列に、次の図のとおりに対応します。

<RecordMappingFigure />

出来事の記録を1つのテーブルにまとめると、記録する出来事を追加してもテーブルは増えません。その代わり、出来事ごとに異なる値は、DB による検査の対象から外れます。整合性の検査よりも、記録を残すことを優先しました。

### 結果

`visit_cancellations` テーブルからの変更点は、次の4つです。

- `visit_cancellations` というテーブルの名前が表していた「何が起きたか」は、`event_name` の値で表します。
- 来院以外の対象の記録も同じテーブルに保存するので、対象は `target_type` と `target_id` の組で表します。
- 来院の行からは、キャンセルした人と理由は分かりません。`operated_by` や `reason` のように出来事ごとに異なる列は、JSON にして `payload` の1列に保存します。
- `target_state` には、変更後の来院の行をそのまま保存します。`visits` の行はその後も変わりますが、「いつ何が起きたか」と「その時点の状態」の両方を確認できます。

一方で、`payload` と `target_state` の内容は、DB が検査しません。キーの名前を誤っても `INSERT` は成功し、読み取り時に値を取得できません。また、来院の状態を `visits` と `business_events` の両方に保持するので、1行のサイズが大きくなります。

`cancelVisit` は、記録を `business_events` テーブルに追記するように変更します。`visit_cancellations` テーブルは廃止します。`visit_cancellations` テーブルに保存済みの記録は、`business_events` テーブルへ移行する必要があります。

`business_events` テーブルの設計は、[kosui.me の記事](https://kosui.me/posts/2025/05/06/142842)の設計を基にしています。この記事の設計は PostgreSQL 向けで、`event_id` に UUID v7 を使います。予約システムは SQLite を使います。`event_id` は連番にします。予約システムが対応する Node の下限である 24.12.0 では、`crypto.randomUUIDv7` を使えないためです。

### 検討した案

#### 出来事ごとにテーブルを分けたままにする

値の有無を DB が列ごとに検査でき、テーブルの名前から記録の種類が分かります。記録する出来事が1種類の間は、この案で十分です。しかし、記録する出来事を追加するたびに、テーブルと、それを読み取る SQL が増えます。1つの来院に起きた出来事を時刻の順に読むには、すべてのテーブルを参照する必要があります。

#### 「誰が」と「なぜ」を列にする

操作した人と理由を、`payload` ではなく列で保持すると、値の有無を DB が検査でき、JSON から取り出さずに読み取れます。しかし、リマインダーの取り消しを外部システムへ送信した結果のように、操作した人や理由が無い出来事もあります。この2つの列は必須にできないため、DB による検査という利点は得られません。JSON から取り出さずに読み取れる利点は残りますが、列にする値は、すべての出来事が持つ値に限定しました。

#### `target_state` を持たない

1行のサイズが小さくなり、来院の状態を保持する場所は `visits` だけになります。しかし、`visits` の行はその後も変わります。ある時点の状態を後から確認するには、来院の変更をすべて記録して順にたどる必要があります。現時点で記録しているのは来院のキャンセルだけなので、ある時点の状態を記録から復元できません。
