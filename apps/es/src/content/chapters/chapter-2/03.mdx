## 記録を1つのテーブルにまとめる

</div>

<Workspace scenario={chapter2Table}>
<Fragment slot="memo">

- ステータス: <span data-adr-status="proposed">提案</span><span data-adr-status="approved">承認済み</span>
- 日付: 2026-11-09
- 作成者: 同僚

### 状況

この ADR の対象は、動物病院向けの予約システムです。予約システムのリポジトリは `clinic/clinic-api` です。

予約システムは、来院を `visits` テーブルで管理しています。

ADR 1 は、キャンセルした人と理由を後から回答できるように、来院のキャンセルの記録を `visit_cancellations` テーブルに保存する方式を定めています。`visit_cancellations` テーブルは、キャンセルのたびに1行を追記するテーブルです。連番の ID（`id`）、来院の ID（`visit_id`）、キャンセルした人（`operated_by`）、理由（`reason`）、日時（`cancelled_at`）の列を持ちます。来院のキャンセルの処理（`cancelVisit`）は、`visits` テーブルの更新と同じトランザクションで、`visit_cancellations` テーブルに記録を追記します。

`visit_cancellations` テーブルは、テーブルの名前と列の両方が、キャンセルの記録だけを対象にしています。診察の完了の処理（`completeVisit`）にも同じ方式で記録を追加すると、診察の完了を記録するテーブルがもう1つ必要になります。記録する出来事の数が増えると、テーブルの数も増えます。

出来事ごとにテーブルを分割した場合の運用負荷は、次の発表が報告しています。

<Quote source="SRE Kaigi 2026 の発表より">

また、最初は集約やイベントごとにテーブルを分割していましたが、運用負荷が高かったため、必要になるまでは単一テーブルに寄せるようにしました。過剰な設計を避けるという判断です。

</Quote>

この ADR は、出来事の記録を保存するテーブルの構成を決定します。テーブルの構成は、次の3つの基準で比較しました。

- 記録する出来事を追加しても、テーブルと列が増えないこと
- 値の有無を DB が検査できること
- ほかのテーブルの行を指す値に、外部キー制約を設定できること

### 決定

出来事の記録を、1つのテーブルにまとめて保存します。

業務イベントは、業務で起きた1つの出来事を、「誰が」「いつ」「何を」「なぜ」とともに残す記録です。現時点で記録する業務イベントは、来院のキャンセルの1種類だけです。

- 業務イベントは、出来事の種類や対象にかかわらず、`business_events` テーブルに追記します。
- すべての出来事が持つ値は、列で保持します。出来事ごとに異なる値は、JSON にして1つの列に保存します。
- 出来事が起きた時点の対象の状態も、業務イベントと一緒に保存します。
- 対象のデータを削除した後も、業務イベントは残します。

`visit_cancellations` テーブルの列は、`business_events` テーブルの列に、次の図のとおりに対応します。

<RecordMappingFigure />

出来事の記録を1つのテーブルにまとめると、記録する出来事を追加してもテーブルは増えません。出来事ごとに異なる値を JSON にして `payload` の1列に保存すると、列も増えません。その代わり、DB による検査が減ります。DB は、`payload` の中の値の有無を検査しません。`payload` の中の値は列ではないので、外部キー制約を直接は設定できません。来院の ID を保存する `target_id` にも、外部キー制約を設定できません。`target_id` が指すテーブルは、`target_type` によって変わるためです。

3つの基準をすべて満たす案はありません。採用した案は、テーブルと列が増えないことを優先しました。テーブルや列を出来事ごとに追加する案は、記録する出来事が増えるほど、運用の負荷が高くなります。

外部キー制約を設定できることは、優先しませんでした。来院のデータを削除した後も、その来院の業務イベントは残します。業務イベントから `visits` テーブルへ外部キー制約を設定すると、`visits` テーブルを論理削除にせざるを得ません。`visits` テーブルを論理削除にするかどうかは、選択できる状態にします。論理削除は、できるだけ避けます。整合性の検査よりも、記録を残すことを優先しました。

### 結果

- 顧客価値: 動物病院から問い合わせを受けたときに、1つの来院に起きた出来事を、1つのテーブルから時刻の順に読んで回答できます。出来事が起きた時点の来院の状態も回答できます。来院のデータを削除した後も、回答できます。
- 低減するリスク: 記録する出来事が増えるほどテーブルと SQL が増えて、運用の負荷が高くなるリスクを低減します。
- 増大するリスク: `payload` と `target_state` の内容は、DB が検査しません。キーの名前を誤った業務イベントも保存され、問い合わせを受けたときに値を読み取れないリスクが増大します。`payload` の中の値と `target_id` には外部キー制約を設定できないので、存在しない来院を指す業務イベントが保存されても、DB は検出しません。来院の状態を `visits` と `business_events` の両方に保持するので、保存するデータ量も増えます。

### 検討した案

出来事の記録を保存するテーブルの構成は、採用した案と、採用しなかった2つの案を、状況の3つの基準で比較しました。○は基準を満たすこと、△は一部だけ満たすこと、×は満たさないことを表します。

<div data-alternatives-table>

| 案 | テーブルと列が増えない | 値の有無を DB が検査できる | 外部キー制約を設定できる |
|---|---|---|---|
| JSON にして `payload` の1列に保存する（採用） | ○ | × | × |
| 出来事ごとにテーブルを分けたままにする | × | ○ | ○ |
| 出来事ごとに異なる値を列にする | × | × | △ |

</div>

#### 出来事ごとにテーブルを分けたままにする

値の有無を DB が列ごとに検査でき、ほかのテーブルの行を指す列には外部キー制約を設定できます。テーブルの名前から記録の種類も分かります。記録する出来事が1種類の間は、この案で十分です。しかし、記録する出来事を追加するたびに、テーブルと、それを読み取る SQL が増えます。1つの来院に起きた出来事を時刻の順に読むには、すべてのテーブルを参照する必要があります。

#### 出来事ごとに異なる値を列にする

テーブルは1つにまとめ、操作した人と理由のように出来事ごとに異なる値を、`payload` ではなく列で保持する案です。JSON から取り出さずに値を読み取れ、ほかのテーブルの行を指す列には外部キー制約を設定できます。しかし、外部への送信の結果のように、操作した人や理由が無い出来事もあります。出来事ごとに異なる値の列は必須にできないため、値の有無を DB が検査する利点は得られません。`target_id` には、採用した案と同じ理由で、外部キー制約を設定できません。記録する出来事を追加するたびに、列を追加する必要もあります。そのため、列にする値は、すべての出来事が持つ値に限定しました。

#### `target_state` を持たない

`target_state` の列を持つかどうかは、上の比較とは別の決定です。`target_state` の列を持たない場合は、1行のサイズが小さくなり、来院の状態を保持する場所は `visits` だけになります。しかし、`visits` の行はその後も変わります。ある時点の状態を後から確認するには、来院の変更をすべて記録して順にたどる必要があります。現時点で記録しているのは来院のキャンセルだけなので、ある時点の状態を記録から復元できません。

### 参考

`business_events` テーブルの設計は、[kosui.me の記事](https://kosui.me/posts/2025/05/06/142842)の設計を基にしています。この記事の設計は PostgreSQL 向けで、`event_id` に UUID v7 を使います。予約システムは SQLite を使います。`event_id` は連番にします。予約システムが対応する Node の下限である 24.12.0 では、`crypto.randomUUIDv7` を使えないためです。
