## 記録を1つのテーブルにまとめる

</div>

<Workspace scenario={chapter2Table}>
<Fragment slot="memo">

### 状況

ステップ1では、来院のキャンセルを `visit_cancellations` テーブルに記録しました。同じ方法で `completeVisit` にも記録を足すと、診察の完了を記録するテーブルがもう1つ要ります。記録する出来事の数が多くなると、テーブルの数も増えてしまいます。

<Quote source="SRE Kaigi 2026 の発表より">

また、最初は集約やイベントごとにテーブルを分割していましたが、運用負荷が高かったため、必要になるまでは単一テーブルに寄せるようにしました。過剰な設計を避けるという判断です。

</Quote>

### 決定

出来事の記録を1つのテーブルにまとめます。

業務イベントは、業務で起きた1つの出来事を、誰が、いつ、何を、なぜとともに残す記録です。これ以降は、この記録を業務イベントと呼びます。演習で記録する業務イベントは、来院のキャンセルの1種類だけです。

1つにまとめたテーブルが `business_events` です。ステップ1の列を `business_events` の列に移します。

<RecordMappingFigure />

### 結果

- ステップ1でテーブルの名前が表していた「何が起きたか」は、`event_name` の値で表します。
- 来院以外の対象の記録も同じテーブルに入るので、対象は `target_type` と `target_id` の組で表します。
- 来院の行からは、誰がなぜキャンセルしたのかを知ることはできません。`operated_by` や `reason` のように出来事ごとに違う列は、JSON にして `payload` の1列に入れます。
- `target_state` には、変更後の来院の行をそのまま入れます。`visits` の行はこの後も変わりますが、「いつ何が起きたか」と「その時の状態はどうだったか」が両方わかります。
- `payload` と `target_state` の中身は、DB が検査しません。キーの名前を間違えても `INSERT` は成功し、読むときに値が取れません。整合性の検査よりも、まず記録を残すことを優先します。
- ステップ2の開始時点の DB には、`visit_cancellations` テーブルの代わりに `business_events` テーブルを用意してあります。
- 実際のシステムでは、`visit_cancellations` に残した記録を `business_events` へ移す作業が要ります。
- [関連記事](https://kosui.me/posts/2025/05/06/142842)のテーブル設計は PostgreSQL 向けで、`event_id` に UUID v7 を使います。この演習は SQLite を使い、`event_id` を連番にします。参加者の Node の下限である 24.12.0 に `crypto.randomUUIDv7` が無いためです。

### 代替案

| 案 | 利点 | 採用しなかった理由 |
|---|---|---|
| 出来事ごとにテーブルを分けたままにする | 値が入っているかを DB が列ごとに検査し、テーブルの名前で何の記録かが分かります。記録する出来事が1種類のうちは、これで足ります。 | 記録する出来事を増やすたびに、テーブルと、それを読む SQL が増えます。1つの来院に起きた出来事を時刻の順に読むには、すべてのテーブルを見る必要があります。 |
| 「誰が」と「なぜ」を列にする | 操作した人と理由を `payload` に入れずに列にするので、値が入っているかを DB が検査でき、JSON から取り出さずに読めます。 | 外部への送信の結果のように、操作した人や理由が無い出来事もあります。この2つの列を必須にはできないので、DB の検査という利点は得られません。 |
| `target_state` を持たない | 1行が小さくなり、来院の状態を `visits` と `business_events` の両方に持たずに済みます。 | `visits` の行はこの後も変わります。その時点の状態を後から知るには、来院の変更をすべて記録して順にたどる必要がありますが、いま記録しているのは来院のキャンセルだけです。 |
