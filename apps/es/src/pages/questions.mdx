# ハンズオンの後に受けた質問

ハンズオンの後に、参加者から次の懸念を受けました。

業務イベントの記録をビジネスロジックに入れると、システムの規模が大きくなるにつれてレコードが増え続け、記録をやめることも難しくなるのではないか。ログのように特定の仕組みに依存しない形で残すとしても、費用と古い記録の保管が気になる。

このページは、この懸念に答えます。コードを含む詳しい説明は、[フォローアップの記事](https://kosui.me/posts/2026/11/28/event-record-patterns-and-retreat)にあります。

## ハンズオンのコードはビジネスロジックにイベントストアを入れていない

ハンズオンのコードは、ビジネスロジックにイベントストアを入れることを提案していません。`visits` テーブルが現在の状態を持ち、`cancelVisit` が同じトランザクションで `business_events` へ1行を追記します。`cancelVisit` は、キャンセルできるかを判定するときに `visits` だけを読み、`business_events` を読みません。

## ハンズオンの形では記録と状態が食い違うことがある

`cancelVisit` の中で、`visits` を書き換える `UPDATE` 文と、`business_events` へ追記する `INSERT` 文は、別の文です。この2つの文が同じ出来事を表すことは、開発者がテストで確認します。

- `cancelVisit` を通らずに `visits` を書き換える変更は、記録に残りません。
- `payload` のキーの名前を間違えても、`INSERT` は成功します。

ビジネスロジックがイベントを中心にして書かれていないかぎり、この食い違いは避けられません。

## 業務イベントの記録を始める3つの形

### ビジネスロジックをイベント中心に書く

更新処理の関数は、DB に書き込まず、業務イベントを返します。業務イベントは、`payload` に加えて、変更後の状態を持ちます。保存する処理は、業務イベントが持つ変更後の状態を `visits` に書き、同じトランザクションで同じ業務イベントを `business_events` に書きます。`visits` に書く値と `target_state` に書く値は同じ業務イベントから取るので、一致します。

この形でも、現在の状態は `visits` から読みます。記録から現在の状態を組み立て直すことはしません。代わりに、既存の更新処理を書き直す作業が必要です。

### ハンズオンの形で小さく始める

既存の更新処理に `INSERT` 文を1つ足します。ビジネスロジックは変えません。記録と状態の食い違いは残ります。

### 特定の領域だけビジネスロジックをイベント中心に書く

「誰が、いつ、何を、なぜ」を後から問われる領域だけを、業務イベントを返す形に書き直します。ほかの領域は、ハンズオンの形のままにするか、記録を足さないままにします。2つの形は、1つのシステムで併用できます。

## 古い業務イベントを DB の外へ移す

`business_events` の行は増え続けます。しかし、3つの形はどれも `visits` が現在の状態を持ちます。状態を変える処理は古い業務イベントを読まないので、古い業務イベントは DB の外へ移せます。

<Quote source="kosui.me の記事より" href="https://kosui.me/posts/2026/11/28/event-record-patterns-and-retreat">

実務では、DynamoDB の CDC を使ってイベントを受け取り、それを S3 上に Parquet ファイルで書き込むことで、料金・参照しやすさ・完全性のトレードオフを乗り切ったことがあります。

</Quote>

画面やほかの処理が業務イベントを読む場合は、その業務イベントを DB に残します。

## 記録をやめる手順

- ハンズオンの形では、`cancelVisit` から `INSERT` 文を削除します。記録は止まり、`visits` の更新は変わりません。
- ビジネスロジックをイベント中心に書いた形では、保存する処理から `business_events` への `INSERT` 文を削除します。`visits` への書き込みは残るので、現在の状態は失われません。更新処理の関数が業務イベントを返す形は、そのまま残せます。
- どちらの形でも、残った `business_events` の行は、DB の外へ書き出してから削除します。

画面やほかの処理が業務イベントを読んでいる場合は、記録をやめる前に、その画面や処理の代わりを用意します。業務イベントを読む箇所が増えるほど、記録をやめる作業は増えます。
