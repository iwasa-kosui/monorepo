Slack Engineering が 2023 年 4 月に公開した [Real-time Messaging](https://slack.engineering/real-time-messaging/) は、Slack がメッセージをリアルタイムに届ける仕組みを、サーバーの構成から説明した記事です。筆者は Slack の Senior Software Engineer の Sameera Thangudu 氏です。記事によれば、Slack は世界中にメッセージを 500ms で届けています。

本レポートは、この記事の内容を図とアニメーションで追い直したものです。アニメーションは、データがどのサーバーをどの順に通るかを示すために使っています。図は、記事の説明から本レポートが描き起こしたもので、記事に掲載されている図の転載ではありません。

記事に書かれていない内容を補う箇所には、その旨を書いています。また、記事は 2023 年 4 月時点の構成を説明したもので、現在の構成と一致するとは限りません。

## 要点

- クライアントは、最寄りのリージョンの Gateway Server と WebSocket をつなぎ続けます。リアルタイムなイベントは、すべてこの接続を通って届きます
- チャンネルごとの配信は Channel Server が担当します。どの Channel Server が担当するかは、チャンネル ID のコンシステントハッシュで決まります
- メッセージは、Webapp、Admin Server、Channel Server、Gateway Server の順に通ってクライアントに届きます。入力中の表示のように保存しないイベントは、Webapp と Admin Server を通りません
- 配信先は 2 段階で絞られます。Channel Server はチャンネルを購読している Gateway Server だけに送り、Gateway Server はチャンネルを購読しているクライアントだけに送ります

## 1 件の送信が、多数の配信になる

Slack のチャンネルにメッセージを 1 件投稿すると、そのチャンネルにいてオンラインのクライアントすべてに、同じメッセージが届きます。記事はこれをブロードキャストと呼んでいます。Slack は、1 日に数百万件のメッセージを、数百万のチャンネルに届けています。

届け先のクライアントは世界中にいます。記事によれば、多くのユーザーは現地時間の午前 9 時から午後 5 時の間にオンラインになり、午前 11 時と午後 2 時にピークがあります。地域ごとに時間帯がずれるため、ピークの時刻も地域によって異なります。

この配信を成り立たせるには、少なくとも 2 つのことをサーバーが知っている必要があります。1 つは、あるチャンネルのメッセージを受け取るべきクライアントがどれかです。もう 1 つは、そのクライアントがいま、どのサーバーにつながっているかです。以降で見るサーバーの構成は、この 2 つをどこに持たせるかの答えになっています。

## 登場するサーバー

記事には、役割の異なるサーバーが 4 種類登場します。Channel Server、Gateway Server、Admin Server、Presence Server です。いずれも Java で書かれています。このほかに、API を提供する Webapp、プロキシの Envoy、サービス検出の Consul、ハッシュリングを管理する CHARM が登場します。

次の図は、これらの関係を 1 枚にまとめたものです。「次へ」を押すと、サーバーを 1 種類ずつ強調します。

<Figure name="slack-rtm-overview" />

クライアントから出ている経路は 2 本あります。1 本は Webapp への API 呼び出しです。Webapp は Hacklang で書かれたコードベースで、クライアントが呼び出す API を提供しています。もう 1 本は WebSocket の接続で、こちらは最寄りのエッジリージョンに向かいます。メッセージを送るときは前者を、リアルタイムなイベントを受け取るときは後者を使います。

Gateway Server（以下 GS）は、クライアントと Channel Server の間に立つサーバーです。ユーザーの情報と、WebSocket ごとのチャンネルの購読をメモリに持ちます。ほかのサーバーと違い、GS は複数のリージョンに配置されています。クライアントが近くのリージョンに接続できるようにするためです。あるリージョンに障害が起きたときは、そのリージョンのユーザーを最寄りの正常なリージョンへ切り替える仕組みがあります。

Channel Server（以下 CS）は、チャンネルごとの配信を担当するサーバーです。状態をメモリに持ち、チャンネルの履歴の一部も保持します。1 台の CS は、全チャンネルのうち一部を受け持ちます。記事によれば、ピーク時には 1 台あたり約 1,600 万のチャンネルを受け持ちます。

Admin Server（以下 AS）は、Webapp と CS の間をつなぐサーバーです。状態を持ちません。

Presence Server（以下 PS）は、どのユーザーがオンラインかをメモリに持つサーバーです。Slack の画面でユーザー名の横に出る、緑色の丸の表示を支えています。

## チャンネル ID から担当の CS を決める

あるチャンネルを担当する CS は、チャンネル ID のコンシステントハッシュで決まります。

記事の「チャンネル」は、Slack の画面に並ぶチャンネルだけを指す言葉ではありません。ユーザー、チーム、エンタープライズ、ファイル、ハドル、通常のチャンネルといったものに ID が割り当てられ、そのすべてを抽象的にチャンネルと呼んでいます。何かの更新をリアルタイムに届けたい対象を、まとめてチャンネルとして扱っていると読めます。

コンシステントハッシュは、キーとサーバーを同じ輪の上に並べ、キーの位置から決まった方向にたどって最初に出会うサーバーを担当にする方式です。サーバーを 1 台入れ替えても、担当が変わるのはそのサーバーの担当範囲のキーだけで済みます。この段落と次の図の「チャンネルの割り当て」は、方式の一般的な説明です。Slack の実装がリングをどう構成しているかは、記事には書かれていません。

<Figure name="slack-rtm-hash-ring" />

この方式には、配信の経路を決めるうえで都合のよい性質があります。チャンネル ID さえ分かれば、ハッシュを計算するだけで担当の CS が決まります。必要なのはリングの設定だけで、チャンネルごとの対応表をどこかに問い合わせる必要がありません。後の節で見るとおり、AS も GS も、この計算でメッセージの送り先を決めています。

リングを管理しているのは、CHARM と呼ばれるサーバーです。Consistent Hash Ring Manager の略です。CHARM は、不健全な CS を新しい CS に入れ替えます。記事によれば、新しい CS は 20 秒未満でトラフィックを受けられる状態になります。図のタブを「CS の入れ替え」に切り替えると、この様子を確認できます。

入れ替えの影響は限定的です。1 つのチームのチャンネルは、すべての CS に分散して割り当てられています。そのため、1 台の CS に割り当てられているのは、どのチームについてもチャンネルの一部だけです。CS を入れ替えている間は、その CS が担当するチャンネルのユーザーだけが、20 秒未満の配信の遅れを経験します。

CS は、サービス検出の仕組みである Consul に登録されます。リングの定義は CHARM が管理し、AS と CS は Consul に問い合わせて最新の設定を取得します。

## クライアントが接続を確立するまで

Slack のクライアントは、Slack のサーバーとの間に WebSocket の接続を張り続けます。この接続を通じてリアルタイムにイベントを受け取り、手元の状態を最新に保ちます。

次の図は、クライアントが起動してから、イベントを受け取れる状態になるまでの流れです。

<Figure name="slack-rtm-client-setup" />

1. クライアントが、ユーザーのトークンと WebSocket の接続情報を Webapp から取得します
2. クライアントが、最寄りのエッジリージョンに向けて WebSocket の接続を開始します
3. Envoy が、接続を GS へ転送します。Slack は Envoy を、サービス間のロードバランシングと TLS の終端に使っています
4. GS が、ユーザーの情報を Webapp から取得します。この情報には、ユーザーが所属するすべてのチャンネルが含まれます
5. GS が、最初のメッセージをクライアントへ送ります
6. GS が、ユーザーのチャンネルを持つ CS を購読します。どの CS がチャンネルを持つかは、コンシステントハッシュで決まります。この購読は非同期に進みます

この手順で、状態が 2 か所にできます。GS には「この WebSocket は、これらのチャンネルを購読している」という状態ができます。CS には「このチャンネルは、これらの GS が購読している」という状態ができます。メッセージの配信は、この 2 つの状態をたどって進みます。

## メッセージが届くまで

接続が確立したあとの、メッセージの流れを見ます。記事と同じ例を使います。クライアント A と B は同じエッジリージョンにつながっていて、クライアント C は別のリージョンにつながっています。A がメッセージを送ります。

<Figure name="slack-rtm-message-flow" />

1. A が Webapp の API を呼び、メッセージを送信します。送信は WebSocket ではなく、API 呼び出しで行います
2. Webapp が、メッセージを AS へ渡します
3. AS が、メッセージのチャンネル ID を見て、コンシステントハッシュのリングから担当の CS を見つけ、その CS へメッセージを渡します
4. CS が、そのチャンネルを購読している世界中のすべての GS へ、メッセージを送ります
5. メッセージを受け取った各 GS が、そのチャンネルを購読している接続中のクライアントすべてへ、メッセージを送ります

送信と受信で経路が違うことが、この流れの特徴です。送信は Webapp への API 呼び出しで、受信は GS との WebSocket です。

## 2 段階の購読で配信先を絞る

手順 4 と 5 を、購読という観点でもう少し詳しく見ます。CS は GS 単位の購読を、GS はクライアント単位の購読を持っています。

次の図では、`#dev` というチャンネルに 1 件のメッセージが届きます。GS は 3 台あり、クライアントは A から F まで 6 つあります。`#dev` に入っているのは A、B、C の 3 つです。GS とクライアントの数は、説明のための例です。

<Figure name="slack-rtm-fanout" />

CS は、`#dev` を購読している GS-1 と GS-2 だけにメッセージを送ります。GS-3 につながっているクライアントは誰も `#dev` に入っていないので、GS-3 には送りません。GS-1 は、つながっているクライアントのうち `#dev` を購読している A と B だけにメッセージを送ります。

ここからは記事に書かれていない、本レポートの解釈です。この分担には、次の利点があると読めます。CS は、個々のクライアントの接続を知る必要がありません。クライアントの接続や切断で変わる状態は、GS の中に閉じます。また、CS からリージョンをまたいで送るメッセージは GS ごとに 1 件で済み、クライアントの数だけ増えるのは、クライアントに近い GS から先の区間になります。

記事は、1 件の受信に対する配信の数が、リージョンによって違うことにも触れています。チームの大きさの違いが理由かもしれない、と記事は述べています。

## メッセージ以外のイベント

チャットのメッセージのほかにも、クライアントの状態を変えるリアルタイムな更新があります。記事はこれをイベントと呼んでいます。リアクションの追加、ブックマークの追加、チャンネルへのメンバーの参加などで、イベントの種類は数百あります。これらのイベントは、メッセージと同様の経路で届きます。

記事には、メッセージの配信数のグラフが載っています。このグラフには、一定の間隔で鋭い山があります。記事はこの山の理由を、リマインダー、予約投稿、カレンダーのイベントが毎時 0 分に集中するためだと説明しています。

### 保存しないイベント

イベントの中には、データベースに保存しないものがあります。記事はこれを一時的なイベントと呼び、例として、チャンネルやドキュメントでユーザーが入力中であることを示す表示を挙げています。

一時的なイベントは、メッセージと少し違う経路を通ります。先ほどと同じ配置で、A が入力を始めたときの流れを見ます。

<Figure name="slack-rtm-transient-flow" />

1. A が、入力中のイベントを WebSocket で GS へ送ります
2. GS が、イベントのチャンネル ID を見て、コンシステントハッシュのリングから担当の CS を見つけ、その CS へイベントを渡します
3. CS が、そのチャンネルを購読している世界中のすべての GS へ、イベントを送ります
4. イベントを受け取った各 GS が、そのチャンネルを購読しているユーザーの WebSocket すべてへ、イベントを送ります

図のタブを「メッセージ（比較）」に切り替えると、違いは CS に届くまでの区間だけだと分かります。メッセージは Webapp と AS を通って CS に届きます。入力中のイベントは、すでに張ってある WebSocket を逆向きに使い、GS から直接 CS に届きます。CS から先は同じ経路です。

## プレゼンスは見えている範囲だけ届く

ユーザーがオンラインかどうかの情報は、PS が持っています。ユーザーは、ハッシュによって個々の PS に割り当てられます。クライアントは WebSocket を通じて PS に照会し、GS がその照会と変更の通知を中継します。

記事によれば、クライアントが受け取るプレゼンスの通知は、その時点でアプリの画面に見えているユーザーの分だけです。

<Figure name="slack-rtm-presence" />

ここからは本レポートの解釈です。大きなワークスペースには多数のユーザーがいて、誰かがオンラインやオフラインになるたびに通知が発生します。1 人の変更をほかの全員に届ける方式では、通知の総数がユーザー数の 2 乗に比例して増えます。画面に見えている範囲に絞れば、1 つのクライアントが受け取る通知の数は、ワークスペースの大きさではなく画面に見えている人数で決まります。

## 規模と今後

記事は最後に、この構成が扱っている規模を挙げています。サーバーは 1 台あたり数千万のチャンネルを受け持ち、数千万のクライアントが接続しています。そして、世界中に 500ms でメッセージを届けています。

記事は、この構成が線形にスケールすると述べたうえで、さらに大きな顧客に対応するための拡張に取り組んでいると書いています。

## 記事に書かれていないこと

リアルタイムな配信の設計では、次のような点も論点になります。記事はこれらに触れていないため、本レポートでも説明していません。

- メッセージをいつ、どこに保存するか。記事は、一時的なイベントをデータベースに保存しないと述べていますが、通常のメッセージの保存については説明していません
- クライアントが切断している間に届かなかったメッセージを、再接続のあとにどう取り戻すか
- 同じチャンネルの中で、メッセージの順序をどう保証するか
- CS を入れ替えたとき、CS がメモリに持っていた履歴と購読がどう引き継がれるか
