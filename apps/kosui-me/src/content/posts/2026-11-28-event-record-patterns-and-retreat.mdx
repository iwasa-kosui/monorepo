## はじめに

YAPC で、「[もう他人ごとじゃないイベントソーシング](https://es.kosui.workers.dev)」というハンズオンを行いました。既存のテーブルと更新処理はそのままにして、更新処理に1か所、業務で起きた出来事の記録を足すという内容です。

ハンズオンの後、聴講した参加者から懸念をいただきました。業務イベントの記録を業務ロジックに入れてしまうと、スケールに合わせてレコードが肥大化し、しかもやめづらくなってしまうのではないか。ログのようにロックインされない形で残すのはよいとしても、コストとアーカイブが気になる、という懸念です。

そこで本記事では、この懸念を払拭することを目指します。具体的には、業務イベントの記録を始める3つのパターンを紹介したうえで、記録を DB に持ち続けない方法と、いざという時の撤退戦まで紹介します。

## ハンズオンのコードがしていたこと

先に補足すると、今回のコードは、ビジネスロジックにイベントストアを入れることは提案していませんでした。ハンズオンで書いたのは、次の関数です。

```typescript
export const cancelVisit = (db: DatabaseSync, input: { visitId: string; reason: string; operatedBy: string }): void => {
  withTransaction(db, () => {
    const visit = db.prepare(`SELECT status FROM visits WHERE id = ?`).get(input.visitId);
    if (visit === undefined) {
      throw new Error('来院が見つかりません');
    }
    if (visit.status === 'completed') {
      throw new Error('診察が終わった来院はキャンセルできません');
    }
    db.prepare(`UPDATE visits SET status = 'cancelled' WHERE id = ?`).run(input.visitId);
    const cancelled = db.prepare(`SELECT * FROM visits WHERE id = ?`).get(input.visitId);
    db.prepare(`
      INSERT INTO business_events (event_at, event_name, payload, target_id, target_type, target_state)
      VALUES (?, ?, ?, ?, ?, ?)
    `).run(
      new Date().toISOString(),
      'VisitCancelled',
      JSON.stringify({ reason: input.reason, operatedBy: input.operatedBy }),
      input.visitId,
      'Visit',
      JSON.stringify(cancelled),
    );
  });
};
```

`visits` テーブルは、今も現在の状態を持っています。足したのは、来院のキャンセルと同じトランザクションの中で、`business_events` テーブルへ1行を追記する `INSERT` 文だけです。記録から現在の状態を組み立て直すことも、イベントソーシング専用の製品を導入することもしていません。

しかし、業務イベントを記録するやり方は、この形だけではありません。やり方はいくつかあります。それぞれを紹介する前に、ハンズオンの形の限界を率直に書いておきます。

## ペイロードと状態は乖離しうる

結局、ビジネスロジック自体がイベントを中心にして書かれていないと、業務イベントのペイロードと状態が乖離することは避けられません。

ハンズオンのコードでは、`visits` を書き換える `UPDATE` 文と、`business_events` へ追記する `INSERT` 文は、別々の文です。この2つの文が同じ出来事を表していることは、コードを書いた開発者が保証するしかありません。例えば、`cancelVisit` を通らずに `visits` を書き換える処理が後から増えれば、その変更は記録に残りません。`payload` のキーの名前を間違えても、`INSERT` は成功します。

<Figure name="event-record-path-bypass" />

この乖離を防ぐには、状態テーブルに書く値と、業務イベントとして残す値の出どころを一つにする必要があります。つまり、ビジネスロジックが業務イベントを返し、状態テーブルにはその業務イベントから取った値を書く形です。

## パターン1: 小さく始める

一つ目は、ハンズオンのように小さく始めるパターンです。既存の更新処理に `INSERT` 文を1つ足すだけで、ビジネスロジックは変えません。

このパターンでは、ペイロードと状態の乖離は残ります。それでも、私はこのパターンから始める価値があると考えています。一度失われてしまったデータを復元することは二度とできませんが、記録を足した日から先の出来事は残せるからです。

乖離は、後から検出することもできます。ハンズオンの第4章では、集計テーブルの値と、業務イベントから数え直した値を比べる関数を書きました。ただし、この比較で分かるのは、差があることまでです。

## パターン2: ビジネスロジックをイベント中心に書く

二つ目は、先に述べた形を実践するパターンです。ビジネスロジックが業務イベントを返し、状態テーブルにはその業務イベントから取った値を書きます。[以前の記事](https://kosui.me/posts/2025/05/06/142842)で紹介した設計がこれに当たります。以前の記事では、業務イベントに当たるものをドメインイベントと呼んでいました。

ハンズオンの来院のキャンセルをこのパターンで書き直すと、ビジネスロジックは次のようになります。

```typescript
const cancel = (
  visit: Visit,
  input: Readonly<{ reason: string; operatedBy: string }>,
  now: Date,
): VisitCancelled => {
  if (visit.status === 'completed') {
    throw new Error('診察が終わった来院はキャンセルできません');
  }
  return VisitEvent.create(
    visit.id,
    { ...visit, status: 'cancelled' },
    'VisitCancelled',
    { reason: input.reason, operatedBy: input.operatedBy },
    now,
  );
};

export const Visit = { cancel } as const;
```

`Visit.cancel` は DB に触れず、何が起きたかを表す業務イベントを返します。業務イベントは、ペイロードに加えて、変更後の状態を持ちます。

業務イベントを保存するストアは、次のようになります。

```typescript
export const createSqliteVisitCancelledStore = (db: DatabaseSync): VisitCancelledStore => ({
  store: (event) => {
    db.prepare(`UPDATE visits SET status = ? WHERE id = ?`).run(event.targetState.status, event.targetId);
    db.prepare(`
      INSERT INTO business_events (event_at, event_name, payload, target_id, target_type, target_state)
      VALUES (?, ?, ?, ?, ?, ?)
    `).run(...toBusinessEventRow(event));
  },
});
```

ストアは、業務イベントが持つ変更後の状態を `visits` に書き、同じ業務イベントを `business_events` に書きます。`visits` に書く値と `target_state` に残す値は同じ業務イベントから取るので、この2つは一致します。

<Figure name="event-record-event-centered" />

集約と業務イベントの型、ユースケース、テストを含む全体は、次のエディタで読めます。ディレクトリの分け方は、実際のアプリに合わせています。ツアーの「次へ」を押すと、来院のキャンセルが処理される順に、コードをたどれます。

<CodeEditor name="event-centered" title="来院のキャンセルを、業務イベントを返す関数と保存する処理で書いたコード" />

このパターンでも、イベントストアは入れていません。現在の状態は今までどおり `visits` から読み、記録から状態を組み立て直すこともしません。ビジネスロジックが依存しているのは、業務イベントの型だけです。

もちろん、このパターンでも乖離が完全になくなるわけではありません。ストアを通らずに DB を直接書き換えれば、その変更は記録に残りません。ペイロードと変更後の状態を組み立てるのは `Visit.cancel` なので、この2つの対応は `Visit.cancel` のテストで保証することになります。しかし、ここで私が指摘したいのは、確認すべき場所が、DB に触れない関数1つとストア1つに集まるということです。

一方、このパターンには大きなコストがあります。既存の更新処理を、業務イベントを返す関数とストアに書き直さなければなりません。既存のシステムの全体を一度に書き直すのは、フルリプレイスと同じく、ダウンタイムやバグのリスクが大きすぎます。

## パターン3: 特定の領域だけビジネスロジックをイベント中心にする

三つ目は、特定の領域だけビジネスロジックをイベント中心にするパターンです。パターン1とパターン2は、1つのシステムの中で併用できます。

イベント中心に書き直す領域は、「誰が、いつ、何を、なぜ」を後から問われる、クリティカルな領域から選びます。それ以外の領域は、パターン1のままにするか、記録を足さないままにします。

私が個人で開発している Fediverse のサーバー [iori](https://github.com/iwasa-kosui/monorepo/tree/main/apps/iori) も、このパターンです。投稿やリポストは、イベントを返す関数とストアで書いています。一方、アクセストークンの最終利用日時の更新や、翻訳結果の保存は、状態テーブルを直接書き換えていて、イベントを作っていません。

## 記録を DB に持ち続けない

次に、レコードの肥大化とコストの懸念です。どのパターンでも、`business_events` の行は増え続けます。

しかし、増え続ける業務イベントを、DB に持ち続ける必要はありません。3つのパターンはどれも、現在の状態を状態テーブルが持っています。状態を変える処理は古い業務イベントを読まないので、古い業務イベントは DB の外へ移せます。

<Figure name="event-record-archive" />

実務では、DynamoDB の CDC を使ってイベントを受け取り、それを S3 上に Parquet ファイルで書き込むことで、料金・参照しやすさ・完全性のトレードオフを乗り切ったことがあります。DynamoDB 以外では、Aurora PostgreSQL の Outbox テーブルに届いたイベントを、Iceberg/Delta Lake 形式で S3 へ書き出す ECS のワーカーを立てたこともあります。DB に置き続ければ、参照しやすく、記録も抜けませんが、料金がかさみます。ログとして出力すれば料金は抑えられますが、ログの出力は DB のトランザクションに入らないので、出力に失敗すると記録が抜けます。業務イベントを状態と同じトランザクションで DB に書いておけば、DB に書かれた業務イベントを CDC やワーカーで受け取り、S3 へ書き出せます。

ログのようにロックインされない形で残すという考え方とも、この形は両立します。書き込みは DB のトランザクションに任せ、保管はログと同じように DB の外へ出すからです。Parquet は特定の DB に依存しないファイル形式なので、DB を変えても記録は読めます。

iori でも同じ考え方で、7日より古いイベントを毎日 Cloudflare R2 に Parquet で書き出し、書き出しに成功した範囲だけを D1 から削除する[処理](https://github.com/iwasa-kosui/monorepo/blob/main/apps/iori/src/useCase/archiveDomainEvents.ts)を実装しています。

ここで注意が必要なのは、業務イベントを読む機能です。iori は、アカウントの作成日時を、イベントのテーブルから読んでいます。そのため、アカウントの作成のイベントは、書き出しの後も D1 に残しています。業務イベントを読む機能が増えるほど、DB に残すものも増えます。

## いざという時の撤退戦

最後に、やめづらくなるという懸念です。記録をやめる手順は、パターンによって変わります。

パターン1は、最も簡単にやめられます。更新処理から `INSERT` 文を消せば、記録は止まります。`visits` の更新は何も変わりません。残った `business_events` の行は、S3 などへ書き出してから削除します。

パターン2とパターン3では、ストアから `business_events` への `INSERT` 文を消します。`visits` への書き込みは残るので、現在の状態は失われません。ビジネスロジックが業務イベントを返す形は、そのまま残せます。業務イベントは関数の戻り値として残るだけで、どこにも記録されなくなります。パターン3であれば、書き直した領域が限られている分、元の形に戻す場合の手間も小さくなります。

どのパターンでも撤退を難しくするのは、業務イベントを読む機能です。画面や別の処理が業務イベントを読んでいると、記録をやめる前に、その機能の代わりを用意しなければなりません。いざという時にやめられる状態を保ちたいなら、業務イベントを読む箇所を把握しておくべきです。

3つのパターンのどれでも撤退できるのは、状態テーブルを残しているからです。状態テーブルを持たず、記録から現在の状態を組み立て直す設計にすると、記録をやめる前に、現在の状態をテーブルへ書き出す移行が必要になります。

記録を監査に使っている場合は、DB から削除する前に、書き出した先で必要な期間だけ保管できることを確認します。

なお、ここに書いた撤退の手順は、私が実際に撤退して確かめたものではなく、設計から導いたものです。

## まとめ

- ハンズオンのコードは、ビジネスロジックにイベントストアを入れていません。状態テーブルを残したまま、同じトランザクションで業務イベントを追記しただけです。
- ペイロードと状態の乖離は、ビジネスロジックがイベントを中心にして書かれていない限り避けられません。小さく始めて、クリティカルな領域から、ビジネスロジックをイベント中心に書き直せます。
- 業務イベントは DB に持ち続ける必要がありません。状態テーブルを残し、業務イベントを読む箇所を把握していれば、記録はやめられます。

業務イベントの記録を始めるか迷っている方の参考になれば幸いです。
