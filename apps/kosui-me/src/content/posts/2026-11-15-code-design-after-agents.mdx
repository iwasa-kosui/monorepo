最近、業務でコードを読むことはほとんどなくなりました。

私は現在、エンジニアというよりも PdM に近い立場で業務をしています。社内ではエージェントを組み合わせた開発の仕組みを運用しており、私が PRD とサービスブループリントを作成すると、そこからロードマップが作成され、Design Doc と ADR で論点が整理されます。私が担当するのは、整理された未決の論点に回答することです。回答に応じて、実装とテストが自動で生成されます。

この状況では、「AI がコードを書くなら、コード設計は不要ではないか」という問いが生じます。コードを読まない人間がコード設計を気にする必要があるのか、という問いです。

## 結論

コードを読まなくなった現在のほうが、コード設計の重要性は高いと考えています。

開発速度を上げても、顧客が認知できる機能の量には上限があります。そのため、差別化要因は開発速度ではなく品質、とくに機能適合性になります。機能適合性を維持するには、PRD に記述したビジネスの関心とコードの構造を一致させ、人もエージェントも重要なロジックに注意を向けられる設計にする必要があります。設計のスタイルは問いません。

## 開発速度は顧客の認知負荷で律速される

機能を多く開発しても、顧客がその機能を正しく認知しなければ、機能は利用されません。利用されない機能は、ビジネス上の価値を生みません。開発は顧客の認知負荷によって律速されます。

エージェントの導入によって、開発できる量は増えました。一方で、顧客が新しい機能を理解して業務に組み込む速度は、開発チームのリリース頻度とは無関係に決まります。

## PRD を起点にした検証の限界

コードを読まない状態で、私は PRD と実装の乖離を次の方法で検出しています。

エージェントにロバストネス図やシーケンス図を作成させています（[以前の記事](https://kosui.me/posts/2025/05/08/011826)で手順を紹介しました）。また、事前に多数のユーザーペルソナを定義し、各ペルソナが操作に迷うケースや業務を継続できなくなるケースがないかを、エージェントに検証させています。

それでも検出できなかった不具合があります。詳細は省略しますが、複数の端末で実施する作業において、あるユーザーが1台の端末で作業を開始していると、別の端末でもその作業を再開する、という振る舞いが実装に含まれていました。この振る舞いは PRD に記述されていませんでした。ユーザーが複数の端末で並行してセットアップを進めると、この振る舞いによって不整合が発生します。

ビジネスと実装の構造が乖離していると、この問題は大きくなります。検証した PRD やモデルと実際のコードが対応しなくなり、検証結果が実装の品質を保証しなくなります。

「型検査、テスト、CI があれば、設計を気にしなくても検証基盤で品質を担保できる」という反論が考えられます。検証基盤は重要です。しかし、検証基盤が検証するのも、誰かが記述した仕様です。コードから PRD への逆方向の確認には、コード内の業務上の判断を、PRD と照合できる形で抽出できる必要があります。

エージェントのコンテキストウィンドウには上限があります。技術的な分岐の解析にコンテキストを消費すると、その分だけ業務上の判断に割り当てられるコンテキストは減ります。人間のレビュアーにも同じ制約があります。

## 設計のスタイルは問わない

どのような設計を採用すべきかについて、私は特定のスタイルにこだわる必要はないと考えています。

たとえば、Rails で ActiveRecord を使いながらクリーンアーキテクチャを無理に適用しても、うまく機能しません。Rails に問題があるのではなく、フレームワークの前提に反する設計を採用すると、業務以外の要素に注意を割かれるためです。重要なのは、注意を向けるべきロジックに注意を向けられる設計を選択することです。

私は TypeScript による関数型ドメインモデリングを採用しています。業務の状態と、状態間の遷移を一か所に集約して記述する手法です。この構造であれば、エージェントにコードから状態遷移図を生成させ、PRD の状態遷移と照合できます。前述の「別の端末で再開する」振る舞いを実装する場合は、名前を持つ遷移として定義されます。PRD に存在しない遷移が追加されたことを、状態遷移図の差分として検出できます。
