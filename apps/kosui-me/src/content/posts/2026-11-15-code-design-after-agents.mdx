最近、業務でコードを読むことはほとんどなくなりました。

私は現在、エンジニアというよりも PdM に近い立場で業務をしています。社内ではエージェントを組み合わせた開発の仕組みを運用しています。私が PRD やサービスブループリントで意図を記述すると、その意図とナレッジベースから、バックログと論点が生成されます。私は論点に回答していき、回答に応じて実装とテストが生成されます。

以前は、私がターミナルでエージェントにプロンプトを入力し、出力を確認してから次の指示を出していました。この方法では、課題ごとに人の入力が必要になり、人が離席すると開発が止まります。現在の仕組みでは、人が入力するのは意図の作成、論点への回答、マージの判断の3つに限られます。

この仕組みでは、エージェントが役割ごとに分かれています。worker は課題を取得して実装し、テストと CI を通します。reviewer は PR をレビューし、指摘は worker が修正します。このループは、指摘が解消されるまで人を介さずに反復されます。未決の論点があっても、worker は回答を待たずに仮の案で実装を進めます。人は台帳のページにあるチェックリストで論点に回答します。PR ごとに解説ページが作成され、人はそれを読んでマージを判断します。retro は振り返りを記録し、スキルの改善を PR として提案します。

ただし、レビュー待ちの PR の数には上限を設けています。人が読み切れない量の PR を作成しても、マージの判断が追いつかないためです。上限に達すると、worker は新しい課題を取得しません。この仕組みのスループットは、最終的に人のレビュー容量で決まります。

この状況では、「AI がコードを書くなら、コード設計は不要ではないか」という疑問が生じます。

## 結論

コードを読まなくなった現在のほうが、コード設計の重要性は高いと考えています。

開発速度を上げても、顧客が認知できる機能の量には上限があります。そのため、差別化要因は品質、とくに機能適合性になります。機能適合性を維持するには、PRD に記述したビジネスの関心とコードの構造を一致させ、人もエージェントもビジネスロジックを把握しやすい設計にする必要があります。設計のスタイルは問いません。

## 開発速度は顧客の認知負荷で律速される

機能を多く開発しても、顧客がその機能を正しく認知しなければ、機能は利用されません。利用されない機能は、ビジネス上の価値を生みません。開発は顧客の認知負荷によって律速されます。

エージェントの導入によって、開発できる量は増えました。一方で、顧客が新しい機能を理解して業務に組み込む速度は、開発チームのリリース頻度とは無関係に決まります。

DORA の [AI Capabilities Model](https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model) も、ユーザー中心の視点を欠いたまま AI を導入すると、誤った方向に速く進むだけになりうると指摘しています。

私が担当している薬局の業務は、この認知負荷の制約がとくに強い領域です。1台の端末を複数のユーザーが共有し、執務室には複数台の端末があり、ユーザーは複数の店舗を移動します。

<Figure name="scenario-matrix" />

このような環境で想定外の挙動が発生すると、問い合わせにつながります。問い合わせの対応には人件費がかかるため、想定外の挙動は明確なコストです。顧客シナリオがこれだけ複雑な場合、PRD でユーザーストーリーを網羅的に検討し、その内容が実装に正しく反映されている必要があります。

開発速度で差別化できないのであれば、差別化要因は品質です。品質特性にはさまざまなものがありますが、この記事では、そのうち機能適合性（バグや想定外の挙動がないこと）を扱います。

## PRD を起点にした検証の限界

コードを読まない状態で、私は PRD と実装の乖離を次の方法で検出しています。

エージェントにロバストネス図やシーケンス図を作成させています（[以前の記事](https://kosui.me/posts/2025/05/08/011826)で手順を紹介しました）。また、事前に多数のユーザーペルソナを定義し、各ペルソナが操作に迷うケースや業務を継続できなくなるケースがないかを、エージェントに検証させています。

それでも検出できなかった不具合があります。詳細は省略しますが、複数の端末で実施する作業において、あるユーザーが1台の端末で作業を開始していると、別の端末でもその作業を再開する、という振る舞いが実装に含まれていました。この振る舞いは PRD に記述されていませんでした。ユーザーが複数の端末で並行してセットアップを進めると、この振る舞いによって不整合が発生します。

<Figure name="conflict-sequence" />

この不具合は、私が実際のコードを読んでいた際に、想定外の分岐に気づいたことで判明しました。ペルソナ検証やテストで検出されたものではありません。

ペルソナ検証、図による検証、PRD から作成するテストは、PRD に記述された内容だけを確認します。これらの検証は「PRD からコード」の方向にしか機能しません。実装には存在するが PRD には記述されていない振る舞いは、検証の対象に含まれません。

ビジネスロジックが複数のファイルに分散している構造では、PRD の各項目に対応する箇所を探すために、すべてのファイルを読む必要があります。別の端末で作業を再開するロジックのように、データの取得条件として記述されたビジネスロジックは、照合の対象から漏れやすくなります。

<Figure name="logic-scattered" />

ビジネスと実装の構造が乖離していると、この問題は大きくなります。検証した PRD やモデルと実際のコードが対応しなくなり、検証結果が実装の品質を保証しなくなります。

「型検査、テスト、CI があれば、設計を気にしなくても検証基盤で品質を担保できる」という反論が考えられます。検証基盤は重要ですが、検証基盤が検証する対象も、記述済みの仕様です。コードから PRD への逆方向の確認には、コード内のビジネスロジックを、PRD と照合できる形で抽出できる必要があります。

## ビジネスロジックの配置

ビジネスロジックがデータ構造、検索条件、技術的な分岐の中に埋もれていると、人もエージェントもそのロジックを認識しにくくなります。

エージェントのコンテキストウィンドウには上限があります。技術的な分岐の解析にコンテキストを消費すると、その分だけビジネスロジックに割り当てられるコンテキストは減ります。人間のレビュアーにも同じ制約があります。

PRD に記述されたビジネスの関心と、コードに実装されたビジネスロジックの構造が一致しているほど、変更容易性は高くなり、PRD と実装の乖離も防ぎやすくなります。このため、エージェントがビジネスロジックに集中でき、エージェントにとって認知負荷の低い設計が必要です。

ビジネスロジックが業務の用語で一か所に集約されていれば、人もエージェントも、コードから PRD への逆方向の確認を偶然に依存せず、定常的に実施できます。今回の不具合は、私が偶然コードを読んだことで検出されました。設計によって、この確認を定常的な工程にできると考えています。

## 設計のスタイルは問わない

どのような設計を採用すべきかについて、私は特定のスタイルにこだわる必要はないと考えています。

たとえば、Rails で ActiveRecord を使いながらクリーンアーキテクチャを無理に適用しても、うまく機能しません。フレームワークの前提に反する設計を採用すると、業務以外の要素の理解にコストがかかるためです。フレームワークの前提に沿い、ビジネスロジックを把握しやすい設計を選択します。

私は TypeScript による関数型ドメインモデリングを採用しています。業務の状態と、状態間の遷移を一か所に集約して記述する手法です。画面、API のハンドラ、データベースへのアクセスのような入出力はシステムの端に寄せ、業務の状態と遷移は入出力を持たない処理として中央に置きます。この構造であれば、エージェントにコードから状態遷移図を生成させ、PRD の状態遷移と照合できます。前述の「別の端末で再開する」振る舞いを実装する場合は、名前を持つ遷移として定義されます。PRD に存在しない遷移が追加されたことを、状態遷移図の差分として検出できます。

<Figure name="logic-centralized" />

この設計を採用しても、不適切なコードの記述は防げません。ただし、ビジネスロジックの配置先が決まるため、配置先から外れたコードをレビューで検出しやすくなります。

## おわりに

開発速度で差別化できなくなった現在、差別化要因は機能適合性という品質です。コードを読む機会が減った現在も、ビジネスロジックの所在を人とエージェントの両方が把握できる設計を選択します。

関数型ドメインモデリングの原則は、エージェント向けのスキル [kamae](https://kosui.me/posts/2026/04/08/functional-ts-principles) として公開しています。動物病院の予約とカルテ管理を題材にした[ハンズオン教材](https://fp-with-ts-hands-on.kosui.workers.dev/)（[リポジトリ](https://github.com/iwasa-kosui/fp-with-ts-hands-on)）も公開しており、2026年8月30日にはイベントとして開催しました。設計スタイルの一例として参考にしてください。
