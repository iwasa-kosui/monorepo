私は業務ではかなりPdMに近い立場にあり、業務でコードを読むことはまれになりました。

社内で使っているエージェントの仕組みでは、私がPRDとサービスブループリントを書くと、ロードマップが作られます。続いてDesign DocとADRで論点が整理されます。私が未決の論点に答えていくと、実装とテストが生成されます。この流れの中で、私が実装のコードを読む場面はほとんどありません。

この状況では、次の問いが自然に浮かびます。AIがコードを書くなら、コード設計はもう不要ではないか、という問いです。

この記事は、その問いに対する私の答えです。結論から書くと、コードを読む機会が減っても、コード設計は続ける価値があると考えています。理由は、開発の価値が顧客の認知で頭打ちになり、その結果として機能適合性という品質が差別化要因になるからです。機能適合性を守るには、業務上の判断が人にもエージェントにも見える設計を選んでおく必要があります。設計のスタイルは好きなものでかまいませんが、本当に気にすべきロジックに注意を向けられる設計であることが条件です。

## 開発は顧客の認知で頭打ちになる

どれだけ多くの機能を作っても、顧客がその機能を正しく認知しなければ、機能は使われません。使われない機能はビジネスの価値になりません。開発は、顧客の認知負荷によって律速されます。そのため、開発速度は差別化要因になりません。

DORAが2025年に公開したAI Capabilities Modelも、この方向の指摘をしています。

> in the absence of a user-centric focus, AI adoption can have a negative impact on team performance... AI-assisted development teams may just be moving quickly in the wrong direction.

出典は [Introducing DORA's inaugural AI Capabilities Model](https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model) です。要旨は次のとおりです。利用者に焦点を当てていない状態でAIを導入すると、チームの成果に悪い影響が出ることがあります。AIを使う開発チームは、間違った方向へ速く進んでいるだけかもしれません。

顧客が機能の挙動を予想できないと、問い合わせが増えます。思わぬ挙動は、顧客の戸惑いを問い合わせという形で表に出します。問い合わせの対応には人件費がかかるので、思わぬ挙動は明確なコストになります。

私が関わっている薬局という医療の現場では、1台の端末を複数のユーザーが使います。執務室には複数台の端末があります。ユーザーが複数の店舗を行き来することもあります。顧客のシナリオがとても複雑なので、PRDでさまざまなユーザーストーリーを慎重に考え、それが実装に正しく反映されている必要があります。

開発速度が差別化要因にならないなら、残る差別化要因は品質です。品質にもさまざまな側面がありますが、私が重視するのは機能適合性です。機能適合性は、ISO/IEC 25010が定める品質特性の名前です。私は、バグや思わぬ挙動がないことをこの言葉で指しています。

## PRDを起点にした検証の限界

私は、PRDと実装の乖離を防ぐために、エージェントにロバストネス図やシーケンス図を描かせています。ロバストネス図については、以前に [生成AIにMermaid.jsでロバストネス図を描いてもらう](https://kosui.me/posts/2025/05/08/011826) という記事を書きました。

また、事前に多くのユーザーペルソナを定義しています。そのペルソナが戸惑うケースや、業務を続けられなくなるケースがないかを、エージェントに検証させています。

それでも検証から漏れた事例がありました。ここでは内容をぼかして書きます。

複数の端末で行う作業があります。あるユーザーが既に1台の端末で作業を始めている場合に、別の端末でもその作業をそのまま再開する、という振る舞いが実装に入っていました。この振る舞いはPRDに書かれていませんでした。ユーザーが複数の端末を並行して準備する場面では、この振る舞いによって作業が壊れます。

この振る舞いが分かったのは、私がたまたま実際のコードを読んで、変な分岐を見つけたからです。エージェントによる検証やテストで見つかったわけではありません。

この事例から、次の論点が見えます。PRDを起点にした検証には、ペルソナ検証、図の作成、PRDから作るテストがあります。これらが確認できるのは、PRDに書かれたことだけです。検証の方向は「PRDからコード」です。実装にはあるがPRDにはない振る舞いは、検証の対象に入りません。

ビジネスと実装の形が離れていると、この問題は大きくなります。検証済みのPRDやモデルと実際のコードが別物になり、検証が意味を失いやすくなるからです。PRDの通りに作られているかを確認しても、PRDにない振る舞いが実装に残っていれば、顧客は思わぬ挙動に出会います。

型検査、テスト、CIのような検証の仕組みは重要です。しかし、それらだけでは、コードからPRDへの逆向きの確認はできません。逆向きの確認には、コードの中に何があるかを、PRDと突き合わせられる形で取り出せることが必要です。

## 設計が決めるのは、注意を向ける先

業務上の判断が、データの持ち方、検索条件、技術的なコードの分岐に紛れ込むことがあります。そうなると、人もエージェントも、その判断に気づきにくくなります。

エージェントのコンテキストには上限があります。Anthropicの記事は、コンテキストの扱いを次のように述べています。

> Context, therefore, must be treated as a finite resource with diminishing marginal returns.

出典は [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) です。コンテキストは有限の資源として扱う必要があり、量を増やすほど得られる効果は小さくなる、という意味です。

エージェントが技術的な分岐を読み解くことに多くのコンテキストを使うと、業務上の判断に使える分が減ります。エージェントがなるべくビジネスロジックだけに集中できる、エージェントにとって認知負荷の低い設計が求められます。

PRDに書かれたビジネスの関心と、コードに書かれたビジネスロジックの形が近いほど、変更しやすくなります。PRDと実装の齟齬による仕様からの乖離も、防ぎやすくなります。

業務上の判断が業務の言葉で一か所に現れていれば、人でもエージェントでも、コードからPRDへの逆向きの確認を、偶然に頼らず日常的に行えます。前の節では、私がたまたまコードを読んで変な分岐を見つけました。この偶然を日常に変えることが、設計の役割だと考えています。

## 設計のスタイルは好きなものでよい

設計のスタイルは、究極的には好きなものを適用すればよいと考えています。大事なのは、本当に気にしなければならないロジックに注意を向けられる設計を選ぶことです。

たとえば、RailsでActiveRecordを使いながら、クリーンアーキテクチャを無理に当てはめても、うまくいきません。これはRailsが劣っているという話ではありません。論点は、フレームワークの前提に逆らう設計は、注意を業務以外に向けさせるということです。

私の場合の一例として、TypeScriptによる関数型ドメインモデリングを示します。判別共用体で状態を表し、純粋関数で状態遷移を書き、外部からの入力を境界で検証します。

以下のコード例は、説明のために作った架空の題材です。実在のプロダクトのコードではありません。

まず、業務上の判断が技術的なコードに紛れている例です。

```ts
// 進行中の初期設定をユーザーだけで探しているため、別の端末の作業がそのまま再開される
const setup =
  (await db.deviceSetup.findFirst({ where: { userId, status: "in_progress" } })) ??
  (await db.deviceSetup.create({ data: { userId, deviceId, status: "in_progress" } }));
```

次に、状態と遷移をドメインモデルとして書いた例です。

```ts
type UserId = string & { readonly __brand: "UserId" };
type DeviceId = string & { readonly __brand: "DeviceId" };

type NotStarted = Readonly<{ kind: "NotStarted"; userId: UserId; deviceId: DeviceId }>;
type InProgress = Readonly<{ kind: "InProgress"; userId: UserId; deviceId: DeviceId; startedAt: Date }>;
type Completed = Readonly<{ kind: "Completed"; userId: UserId; deviceId: DeviceId; completedAt: Date }>;

type DeviceSetup = NotStarted | InProgress | Completed;

const DeviceSetup = {
  start: (setup: NotStarted, now: Date): InProgress => ({
    kind: "InProgress",
    userId: setup.userId,
    deviceId: setup.deviceId,
    startedAt: now,
  }),
  complete: (setup: InProgress, now: Date): Completed => ({
    kind: "Completed",
    userId: setup.userId,
    deviceId: setup.deviceId,
    completedAt: now,
  }),
} as const;
```

最後に、「別の端末で再開する」を業務として認めるなら、遷移として名前を付けて書く例です。

```ts
const resumeOnAnotherDevice = (setup: InProgress, deviceId: DeviceId): InProgress => ({
  ...setup,
  deviceId,
});
```

最初の例では、「どの端末の作業か」という業務上の判断が、検索条件の書き方に埋もれています。読み手は、データベースの問い合わせを読まなければ、この判断に気づけません。

2つ目の例では、どの状態からどの状態へ遷移できるかが、DeviceSetupの関数の一覧として一か所に並びます。エージェントにこの一覧から状態遷移図を描かせれば、PRDの状態遷移と突き合わせられます。

3つ目の例のように、別の端末で再開する振る舞いを入れるなら、その振る舞いは名前の付いた遷移として現れます。PRDにない遷移が増えたことが、レビューでも状態遷移図でも見えます。

この設計でも、最初の例のようなコードを書くことは防げません。この設計が変えるのは、業務上の判断を置く場所です。置き場所が決まっているので、そこから外れたコードが目立ちます。

私はこの原則を、エージェント向けのスキル kamae としてまとめて公開しています。作者は私自身です。kamae-tsというスキルプラグインに含まれており、詳しくは [サーバサイドTypeScriptの関数型ドメインモデリングを実践するエージェント向けプラグインを公開](https://kosui.me/posts/2026/04/08/functional-ts-principles) に書きました。

関数型ドメインモデリングのハンズオン教材も公開しています。教材サイトは [fp-with-ts-hands-on](https://fp-with-ts-hands-on.kosui.workers.dev/) で、リポジトリは [iwasa-kosui/fp-with-ts-hands-on](https://github.com/iwasa-kosui/fp-with-ts-hands-on) です。教材は、動物病院の予約とカルテ管理を題材にしています。2026年8月30日には、この教材を使ったハンズオンをイベントとして開催しました。

ハンズオンでは、参加者が業務の事故から問いを言語化し、その問いをエージェントへの依頼文に変えます。その後、型とテストで検証したうえで、班内で相互にレビューする流れにしました。レビューシートには、「型検査では確認できず、テストまたは実行時に確認すること」を書く欄を設けています。

関数型ドメインモデリングは手段の1つです。ほかのスタイルを否定するものではありません。

## まとめ

開発速度が差別化要因にならない時代には、機能適合性という品質が差別化要因になります。顧客の認知で開発が頭打ちになる以上、顧客が思わぬ挙動に出会わないことが、そのまま価値になるからです。

エージェントが書くコードであっても、業務上の判断がどこにあるかを、人にもエージェントにも見えるようにしておく設計を選びます。PRDを起点にした検証は、PRDに書かれたことしか確認できません。コードからPRDへの逆向きの確認を、偶然ではなく日常の作業として行えるようにするのが、設計の役割です。

設計のスタイルは問いません。注意を向けるべきロジックに注意を向けられる設計を選びます。私はその手段として、TypeScriptによる関数型ドメインモデリングを使っています。
