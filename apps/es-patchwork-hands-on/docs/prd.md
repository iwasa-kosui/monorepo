# 「もう他人ごとじゃないイベントソーシング」製品要求書

状態: 講師が承認しました。決定の一覧は[講師が決めること](#講師が決めること)にあります。

このハンズオンの中心の対象者は、イベントソーシングの意味があまり分からないのにコストが高い選択肢だと思っている開発者です。参加者は、全体を移行しなくても必要なエッセンスを部分適用できることを、既存の更新処理で確かめます。参加者の認識が「既存プロジェクトには非現実的」から「部分的かつ意義のある活用ができる」へ変わることを目指します。

## 問題

プロポーザルの概要は、「医療・金融・教育など、社会を支えるプロダクトには、障害や問い合わせ、監査に対して「なぜ現在の状態になったのか」を説明できる品質が必要です。」と述べます。現在の状態だけを持つテーブルは、この問いに答えられません。

同じ概要は、「イベントソーシングはそのために有用ですが、「最初からイベント中心に設計しなければ使えない」「考えることが多く、現実的ではない」と思われがちです。」と続けます。講師もそう考えていました。講師は、問い合わせ、障害、監査の対応で過去を説明できず苦しみ、必要なエッセンスを既存システムへ部分適用するようになりました。

この問題を抱える開発者でも、語を聞いた時点で自分には関係ないと判断する可能性があります（仮説）。いまの資料は語を先に出します。このままでは、最も参加してほしい人が困りごとを確かめる前に離れます（仮説）。

## 対象者

対象者の中心は、イベントソーシングの意味があまり分からないのに、コストが高い選択肢だと思っている開発者です（合意済み）。

プロポーザルの対象者は「イベントソーシングを何となく知っているが既存システムへの導入は現実的でないと感じている人」と「社会を支えるプロダクトの開発に興味がある人」です。この人たちも引き続き対象です。資料の入口は中心の対象者に合わせ、内容はプロポーザルの約束どおりにします。

対象レベルは初級から中級です。前提知識は、SQL の UPDATE と INSERT が読めることです。TypeScript は読めれば十分です。

### 参加前の姿

次の表は、参加前の姿の整理です。参加者本人を調べた記述はないので、参加者に当てはまるかはすべて仮説です。

| 区分 | 内容 | 根拠 |
|---|---|---|
| 思っていること | 意味があまり分からない | 講師の当時の考え |
| 思っていること | その割にコストが高い | 講師の当時の考え |
| 思っていること | 最初からイベント中心に設計しなければ使えない | プロポーザル |
| 思っていること | 考えることが多く、現実的ではない | プロポーザル |
| 思っていること | 既存の監査ログで足りている | 根拠なし |
| 困っていること | なぜ現在の状態になったのかを説明できない | プロポーザル |
| 困っていること | 導入の費用を見積もる材料がない | 根拠なし |

最も重要な仮説は、中心の対象者も過去を説明できない問いを持つことです。問いを持たない人にとっては、足さないことも正しい結論です。

## 目標

参加者が、終了時に次の4つを自分のシステムの言葉で言えることを目標にします。

1. 「この問いには、今のテーブルでは答えられない」
2. 「全体を移行しなくても、更新処理の境界に記録を足せば、足した後の変更を説明できる」
3. 「費用はこの程度で済む。足す前の過去は分からず、記録の漏れも残る」
4. 「3パターンのうち、自分のシステムに近いのはこれだ。何を活用し、何を記録しないかはこれだ」

目標1は「意味があまり分からない」に、目標3は「コストが高い」に答えます。プロポーザルの届けたいことと目標は、次のように対応します。

| 届けたいこと | 目標 |
|---|---|
| 必要なエッセンスを部分適用できる | 目標2 |
| 説明可能性を高められる | 目標1、目標2 |
| 現実的な適用方法を選べる | 目標3、目標4 |

## やらないこと

- 参加者に導入を迫ること
- DDD の語と考え方の説明
- イベントから状態を組み立て直すこと
- 層の分離とドメインモデルの導入
- システム全体の移行の手順
- 特定のイベントストア製品とフレームワークの利用
- 新しい概念の講義のために、演習の時間を減らすこと

参加者は、終了時に DDD を説明できなくてかまいません。

## 要求と受入条件

### 要求1: 入口で疑いを受け止める

導入は、中心の対象者の疑いをそのまま受け止めます。講師が同じように考えていたことと、考えが変わった理由を話します。全面移行の二択ではないことも伝えます。社会を支えるプロダクトに説明できる品質が必要だという文脈も示します。

受入条件: 導入に、プロポーザルの「最初からイベント中心に設計しなければ使えない」「考えることが多く、現実的ではない」が出ます。講師の経験の文面を講師が確認しています。題名の「他人ごと」の意味が分かります。

### 要求2: 語より先に困りごとを見せる

参加者は、用語の説明を読む前に、現在の状態だけでは説明できない問いを確かめます。手元で動かす人は自分の操作で確かめ、見るだけの人は講師の画面で確かめます。参加者は自分のシステムの問いを1つ挙げます。この要求は目標1を支えます。

受入条件: 導入と第1章の本文で、要求1の文を除いて要求4の用語が出ません。第1章に、問いに答えられないことを実行して確かめる手順があります。

### 要求3: 「DDD」の語をなるべく使わない

資料は「DDD」の語をなるべく使いません（合意済み）。

受入条件: 参加者が読むページと配布物に「DDD」と「ドメイン駆動」が0件です。講師は、質問を受けたときにだけこの語を使います。リンク先の記事の中の語は対象外です。

### 要求4: 関連する用語は必要になった後に出す

「イベントソーシング」「業務イベント」「ドメインイベント」は、その語が必要になる場面の後に出します。要求1で疑いを受け止める文は例外です。

受入条件: 題名と要求1の文を除き、読む順で場面より先に出る語がありません。定義のない語がありません。

### 要求5: 費用と限界を実物で示す

資料は、足す費用を実際の変更量と運用の手間で示し、記録の限界も隠しません。プロポーザルの「現実的な運用コスト」に答えるための要求です。この要求は目標3を支えます。

受入条件: 第2章の終わりに、更新処理への変更量が書かれています。参加者向けのページは、足す前の過去は分からないことと、記録を通らない変更も残ることを説明します。判断表に運用コストの行があります。

### 要求6: 3パターンの比較を削らない

集計テーブル、外部システム同期、既存の監査ログの比較は、プロポーザルの約束です。遅れたときに実演を減らしても、判断表で3パターンすべてを比べます。この要求は目標4を支えます。

受入条件: 参加者が判断表で3パターンを同じ軸で比べ、近いパターンを1つ選ぶ時間があります。遅れたときの手順でも、この時間が残ります。

### 要求7: 何を活用し、何を記録しないかを整理する

判断表は、各パターンで何を部分的に活用し、何を記録しないかを示します。この要求は目標4を支えます。

受入条件: 判断表に、この内容の行があります。

### 要求8: エッセンスの中身を示す

まとめは、今日足したものがイベントソーシングのどのエッセンスで、何を足していないかを説明します。この要求は、プロポーザルの「必要なエッセンスを部分適用できる」に答えます。

受入条件: まとめに、イベントソーシングの肯定形の説明と、足したものとの関係があります。

### 要求9: 持ち帰るものを判断にする

まとめは、帰ってから試す1か所を決める手順を示します。各自が記録する業務上のイベントと変更理由を定義するのは、この手順の中です。演習では講師が定義の理由を説明します。自分の問いが無ければ足さなくてよいことも一文で書きます。

受入条件: まとめの手順に、記録する内容と変更理由の書き出しがあります。足さなくてよい場合の一文があります。

### 要求10: 見るだけでも追える

手元でコードを動かす参加者と、ライブコーディングを見るだけの参加者の両方が内容を追えます。

受入条件: 資料の入口に、見るだけでもよいことが書かれています。見るだけの参加者が講師の画面で各章の結果を確かめられます。

### 要求11: 40分を超えない

追加する内容は、既存の内容を削って入れます。3パターンの比較と第2章の演習は削りません。

受入条件: リハーサルの実測が40分以内です。遅れたときの手順が更新後の内容に合っています。

## 40分の制約

| 時間 | 章 | いまの内容 |
|---|---|---|
| 4分 | 導入 | 講師が話す |
| 4分 | 第1章 | テストの実行 |
| 14分 | 第2章 | 説明2分、演習9分、解答の確認3分 |
| 5分 | 第3章 | 記録から問いに答える |
| 10分 | 第4章 | 講師が3パターンを見せる |
| 3分 | まとめ | 持ち帰りの案内 |

合計は40分で、予備はありません。40分に質疑と入れ替えが含まれるかは未確認です。時間配分はリハーサルで実測していません。要求1は導入の4分に、要求2は第1章の4分に、要求6と要求7は第4章の10分に収めます。

## 成功の測り方

主な指標は認識の変化です。導入したくなった人の数は測りません。導入するかどうかは、各自が持ち帰って判断するためです。次の目安はすべて提案です。

| 測るもの | 方法 | 目安 |
|---|---|---|
| 認識の変化 | 開始時と終了時に同じ問いを聞く | 「活用できる」が増える |
| 適用方法の選択 | 終了後のフォーム | 回答者の7割以上が近いパターンを挙げる |
| 中心の対象者の満足 | フォームを開始時の立場別に見る | 過半数が無駄でなかったと答える |
| 所要時間 | リハーサルの実測 | 40分以内 |
| 中心の対象者の反応 | 他チームの人がリハーサルを受ける | 1人以上が受ける |
| 演習の到達（補助） | 手元で動かす人の挙手 | 半数以上が第2章ステップ1を終える |

開始時と終了時の問いは、「既存システムに部分的に活用できると思うか」です。フォームはこの問いに加えて開始時の立場、答えられない問い、近いパターン、時間が無駄でなかったかを聞きます。演習の到達の目安は、講師手順書の「半数に届かなければ解答を見せる」に合わせました。7割と過半数には根拠がなく、当日の結果を読むための仮の値です。

## 講師が決めること

講師は、各項目の推奨案を承認しました。講師の経験の文面と告知の一文は、資料へ載せる前に講師が確認します。

### 題名の「イベントソーシング」

状態: 合意済み。

推奨案: 題名を変えません。導入で「他人ごと」の意味を講師の話として説明します。導入の一文で全面移行の二択ではないと伝えます。事前案内と告知に、中心の対象者にこそ来てほしいという趣旨の一文を足します。

理由: 題名はプロポーザルとして採択され、掲載されています。告知の一文は対象者を掲載文より広げる公開の文なので、文面は講師の確認が要ります。

### 本文の「イベントソーシング」

状態: 合意済み。

推奨案: 本文で使うのは、導入で疑いを受け止める文とまとめだけにします。まとめで、今日足したものがどのエッセンスで、何を足していないかを説明します。

理由: いまの資料には肯定形の定義がありません。参加者は、記録を足した後なら説明を自分の体験と比べられます。

### 「業務イベント」と「ドメインイベント」

状態: 合意済み。

推奨案: 第2章までは「記録」と書きます。第2章で「業務イベント」を一文で定義し、以降はこの語を使います。「ドメインイベント」は、まとめで関連記事を案内する一文だけに使います。

理由: 「業務イベント」はプロポーザルの語で、「ドメインイベント」はプロポーザルにありません。関連記事を読む人には語の対応を示す必要があります。

### テーブル名 `domain_events` と列名 `aggregate_*`

状態: 合意済み。

推奨案: 平易な名前に変えます。新しい名前は、この決定の後に講師と決めます。

理由: 第2章の穴埋めの4空欄のうち3つが `aggregate_*` です。参加者は9分の演習中に、語の意味を問わず書くことになります。費用は小さくありません。`domain_events` は追跡対象の37ファイル107行に、`aggregate_` は33ファイル97行に出ます。この行の多くは演習のスナップショットです。関連記事のテーブル設計とは名前がずれるので、第2章に対応を一文で書きます。

別案は名前を残して意味だけ説明することです。費用は小さく済みますが、要求4を第2章で満たせません。

### 「足さない」の扱い

状態: 合意済み。

推奨案: 判断表に独立した選択肢として足しません。判断表には「何を部分的に活用し、何を記録しないか」の行を足します。主な成功は、認識の変化と、3パターンから適用方法を選べることです。自分の問いが無ければ足さなくてよいことは、まとめに一文で書きます。

理由: プロポーザルの約束は、どう適用するかを選ぶことです。この形なら第4章の時間をほとんど使いません。

### 測り方

状態: 合意済み。

推奨案: 開始時と終了時に同じ問いを聞きます。終了後に1分のフォームを使います。

理由: 目指すものは認識の変化なので、変化を直接聞きます。フォームと挙手を運営が認めるかは未確認です。フォームを置かないなら、まとめでの挙手に置き換えます。

### リハーサルの参加者

状態: 合意済み。

決定: 他チームの人にリハーサルを受けてもらいます。

確かめること: 認識の変化が伝わるか、40分で実現できるか、どこで関心が切れたかを確かめます。

### 講師の経験の文面

状態: 講師の回答を反映した案です。資料へ載せる前に、講師が文面を確認します。

講師の当時の考えは、「意味がない」ではなく、意味があまり分からないのに、その割にコストが高い選択肢だというものです。文面の案は次のとおりです。

> 私は、イベントソーシングの意味があまり分かりませんでした。その割にコストが高い選択肢だと考えていました。しかし、医療 SaaS の共通基盤を担当し、現在の状態しか残っていないデータのために、問い合わせ、障害、監査の対応で過去を説明できず苦しみました。そこから、必要なエッセンスを既存システムへ部分適用するようになりました。

案の根拠は、講師の回答とプロポーザルの概要です。案にない経験や動機を足しません。

### 原稿の構成5項目の扱い

状態: 合意済み。

プロポーザルの原稿には、ハンズオン構成の5項目があります。掲載文には構成の項目がないので、参加者への公開の約束ではなく講師の意図として扱います。

推奨案: 「問いを洗い出す」と「何を記録しないかを整理する」は要求にします。「記録する業務上のイベントと変更理由を定義する」は、演習では講師の説明に留め、まとめの書き出しで各自が行います。

理由: 9分の演習に定義の作業を足すと収まらないと考えます（推測、未実測）。
