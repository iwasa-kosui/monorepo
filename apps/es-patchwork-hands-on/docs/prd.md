# 「もう他人ごとじゃないイベントソーシング」製品要求書

状態: 草案です。講師が方針を示した項目は「合意済み」と書きます。それ以外は提案で、[講師が決めること](#講師が決めること)で確定します。

このハンズオンは、DDD やイベントソーシングに意味がないと思っている開発者に、既存の更新処理へ記録を足す効果と費用を自分の手で確かめてもらいます。参加者が「足さない」と判断しても、理由を言えれば成功とします（提案）。

## 問題

現在の状態だけを持つテーブルは「誰が、いつ、何を、なぜ変えたか」に答えられません。講師は、問い合わせ、障害、監査の対応で過去を説明できず苦しみました。関連記事も、データ変更の記録が監査記録の提出と障害調査で開発者を助けると述べています。

一方で、この問題を抱える開発者でも、DDD やイベントソーシングの語を聞いた時点で自分には関係ないと判断する可能性があります（仮説）。いまの資料は語を先に出し、記録を足す前提で進みます。このままでは、最も参加してほしい人が困りごとを確かめる前に離れます（仮説）。

## 対象者

対象者の中心は、DDD やイベントソーシングに意味がないと思っている開発者です（合意済み）。

プロポーザルの対象者は「イベントソーシングを何となく知っているが既存システムへの導入は現実的でないと感じている人。社会を支えるプロダクトの開発に興味がある人。」です。この人たちも引き続き対象です。資料の設計は、より距離のある中心の対象者に合わせます。

前提知識は、SQL の UPDATE と INSERT が読めることです。TypeScript は読めれば十分です。

### 参加前の姿

次の表は、中心の対象者についての仮説です。プロポーザルと記事に、この人たちを調べた記述はありません。

| 区分 | 仮説 | 根拠 |
|---|---|---|
| 思っていること | 全部を作り替えないと使えない | プロポーザルの対象者に近い |
| 思っていること | 既存の監査ログで足りている | 根拠なし |
| 思っていること | 用語が多く、仕事の困りごとと結びつかない | 語を避けたいという講師の方針 |
| 困っていること | なぜこの状態になったのかに答えられない | 講師の経験のみ |
| 困っていること | 導入の費用を見積もる材料がない | 根拠なし |

最も重要な仮説は、中心の対象者も過去を説明できない問いを持つことです。問いを持たない人にとっては、「足さない」が正しい結論です。

## 目標

参加者が、終了時に次の4つを自分のシステムの言葉で言えることを目標にします。

1. 「この問いには、今のテーブルでは答えられない」
2. 「更新処理の1か所に、同じトランザクションで記録を足せば、足した後の変更には答えられる」
3. 「足す前の過去は分からない。記録の漏れと保存の費用も生じる」
4. 「この機能には足す、または足さない。理由はこれだ」

## やらないこと

- 参加者に、DDD やイベントソーシングの価値を説得すること
- DDD の語と考え方の説明
- イベントから状態を組み立て直すこと
- 層の分離とドメインモデルの導入
- システム全体の移行の手順
- 新しい概念の講義のために、演習の時間を減らすこと

参加者は、終了時に DDD やイベントソーシングを定義できなくてかまいません。

## 要求と受入条件

### 要求1: 語より先に困りごとを見せる

参加者は、用語の説明を読む前に、問いに答えられないことを自分の操作で確かめます。この要求は目標1を支えます。

受入条件: 導入と第1章の本文に、題名の説明を除いて要求3の用語が出ません。第1章に、参加者が自分で実行して答えられないと確かめる手順があります。

### 要求2: 「DDD」の語をなるべく使わない

資料は「DDD」の語をなるべく使いません（合意済み）。語を聞いて離れる人を減らすためです。

受入条件: 参加者が読むページと配布物に「DDD」と「ドメイン駆動」が0件です。講師は、質問を受けたときにだけこの語を使います。リンク先の記事の中の語は対象外です。

### 要求3: 関連する用語は必要になった後に出す

「イベントソーシング」「業務イベント」「ドメインイベント」は、その語が必要になる場面の後に出します。扱いの詳細は講師が決めます。

受入条件: 題名を除き、読む順で場面より先に出る語がありません。定義のない語がありません。

### 要求4: 足す手間と限界を実物で示す

資料は、足す手間を実際の変更量で示し、記録の限界も隠しません。この要求は目標2と目標3を支えます。

受入条件: 第2章の終わりに、更新処理への変更量が書かれています。参加者向けのページは、足す前の過去は分からないことと、記録を通らない変更も残ることを説明します。

### 要求5: 「足さない」を選択肢として扱う

第4章は、3パターンの比較に「足さない」を加えます。資料は参加者に導入を迫りません。この要求は目標4を支えます。

受入条件: 判断表で、「足さない」を3パターンと同じ軸で比べられます。判断表は、足さないほうがよい場面を1つ以上示します。

### 要求6: 持ち帰るものを判断にする

まとめは、帰ってから試す1か所を決める手順に加えて、足さないと決めた場合に理由を書く手順を示します。この要求は目標4を支えます。

受入条件: まとめの手順が、足す場合と足さない場合の両方で終わります。

### 要求7: 40分を超えない

追加する内容は、既存の内容を削って入れます。

受入条件: リハーサルの実測が40分以内です。遅れたときの手順が更新後の内容に合っています。

## 40分の制約

| 時間 | 章 | いまの内容 |
|---|---|---|
| 4分 | 導入 | 講師が話す |
| 4分 | 第1章 | テストの実行 |
| 14分 | 第2章 | 説明2分、演習9分、解答の確認3分 |
| 5分 | 第3章 | 記録から問いに答える |
| 10分 | 第4章 | 講師が3パターンを見せる |
| 3分 | まとめ | 持ち帰りの案内 |

合計は40分で、予備はありません。40分に質疑と入れ替えが含まれるかは未確認です。時間配分はリハーサルで実測していません。要求1は第1章の4分に、要求5は第4章の10分に収めます。

## 成功の測り方

次の目安はすべて提案です。導入したくなった人の数は測りません。説得を成功として数えることになるためです。

| 測るもの | 方法 | 目安 |
|---|---|---|
| 所要時間 | リハーサルの実測 | 40分以内 |
| 中心の対象者の反応 | 懐疑的な人にリハーサルを受けてもらう | 1人以上が受ける |
| 参加者の立場 | 開始時の挙手 | 記録のみ |
| 演習の到達 | 第2章ステップ1の完了を挙手で確かめる | 半数以上 |
| 判断の結果 | 終了後のフォーム | 回答者の7割以上が書ける |
| 中心の対象者の満足 | フォームを開始時の立場別に見る | 過半数が無駄でなかったと答える |

フォームでは、開始時の立場、答えられない問いを挙げられたか、足す1か所または足さない理由、時間が無駄でなかったかを聞きます。演習の到達の目安は、講師手順書の「半数に届かなければ解答を見せる」に合わせました。7割と過半数には根拠がなく、当日の結果を読むための仮の値です。

## 講師が決めること

各項目の推奨案は、この草案の前提です。

### 題名の「イベントソーシング」

推奨案: 題名を変えません。事前案内と告知に、「DDD やイベントソーシングに意味がないと思っている人にこそ来てほしい」という趣旨の一文を足します。

理由: 題名はプロポーザルとして掲載済みで、変更できるかは未確認です。題名で離れる人には、題名以外の文で届けます。導入の冒頭でも、全面的な採用を勧める会ではないと一文で伝えます。

### 本文の「イベントソーシング」

推奨案: 本文で使うのは、導入の冒頭の一文とまとめだけにします。まとめで、今日足したものとの関係を肯定形で説明します。

理由: いまの資料には肯定形の定義がありません。参加者は、記録を足した後なら、定義を自分の体験と比べられます。

### 「業務イベント」と「ドメインイベント」

推奨案: 第2章までは「記録」と書きます。第2章で「業務イベント」を一文で定義し、以降はこの語を使います。「ドメインイベント」は、まとめで関連記事を案内する一文だけに使います。

理由: 「業務イベント」はプロポーザルの語です。「ドメインイベント」は関連記事の語なので、記事を読む人には対応を示す必要があります。

### テーブル名 `domain_events` と列名 `aggregate_*`

推奨案: 平易な名前に変えます。新しい名前は、この決定の後に講師と決めます。

理由: 第2章の穴埋めの4空欄のうち3つが `aggregate_*` です。参加者は9分の演習中に、この語の意味を問わず書くことになります。費用は小さくありません。`domain_events` は追跡対象の37ファイル107行に、`aggregate_` は33ファイル97行に出ます。この行の多くは演習のスナップショットです。関連記事のテーブル設計とは名前がずれるので、第2章に対応を一文で書きます。

別案は名前を残して意味だけ説明することです。費用は小さく済みますが、要求3の「語より先に場面」を第2章で満たせません。

### 成功に「足さない」を含めるか

推奨案: 含めます。

理由: 導入を成功とすると、中心の対象者への説得になります。プロポーザルの「自分のシステムに合う現実的な適用方法を選べる」とも両立します。プロポーザルの「部分適用できる」は、演習の結果として伝えます。

### 測り方

推奨案: 開始時の挙手と、終了後のフォームを使います。フォームの回答時間は1分を目安にします。

理由: 40分に調査の時間を増やせません。フォームと挙手を運営が認めるかは未確認です。フォームを置かないなら、まとめでの挙手に置き換えます。

### リハーサルの参加者

推奨案: DDD やイベントソーシングを疑っている人を1人以上招いて、リハーサルを受けてもらいます。

理由: 対象者の像はすべて仮説です。本番の前に確かめられる唯一の機会です。誰に頼むかは講師にしか決められません。
