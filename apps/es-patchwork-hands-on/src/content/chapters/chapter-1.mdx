## 問い合わせに答えてみる

事前準備で展開したディレクトリの中にある `chapter-1-start` に移動して、次のコマンドを実行します。見るだけの人は、講師の画面で同じ結果を確かめます。

```bash
node show-visits.ts
```

`ExperimentalWarning: SQLite is an experimental feature` という警告が出ても問題ありません。実行すると、`visits` テーブルの行が出ます。

```text
┌─────────┬───────────────┬──────────┬─────────────┐
│ (index) │ id            │ pet_name │ status      │
├─────────┼───────────────┼──────────┼─────────────┤
│ 0       │ 'visit-pochi' │ 'ポチ'   │ 'cancelled' │
│ 1       │ 'visit-tama'  │ 'タマ'   │ 'cancelled' │
└─────────┴───────────────┴──────────┴─────────────┘
```

この行を見て、「この来院がキャンセルになっているのはなぜですか」に答えてみます。`show-visits.ts` は `visit-pochi` をキャンセルするときに、理由と操作した人を `cancelVisit` に渡しています。しかし、どちらも行に残っていません。この行から読み取れるのは、来院がキャンセルされたことだけです。誰が、いつ、なぜキャンセルしたのかには答えられません。

## 自分のシステムの問いを1つ挙げる

自分のシステムで、現在の状態だけでは答えられない問いを1つ挙げます。次に、その問いの答えが入る列が今のテーブルにあるかを思い出します。問いが思いつかないときは、題材の問いで進めます。

## テストを実行する

同じディレクトリで、次のコマンドを実行します。

```bash
node --test visits.test.ts
```

実行すると、4件が成功して4件が失敗します。ここでは失敗して正常です。次の例は出力の一部です。

```text
▶ 既存の業務
  ✔ 予約した来院をキャンセルすると、来院の状態がキャンセルになる
  ✔ 診察が終わった来院はキャンセルできない
  ✔ キャンセルできなかったときは、記録を残さない
  ✔ 来院の更新に失敗したら、記録も残らない
▶ 第2章 ステップ1
  ✖ 来院をキャンセルすると、来院キャンセルの記録が1行残る
  ✖ キャンセルの記録に、キャンセル後の来院の状態が残る
  ✖ 記録に失敗したら、来院のキャンセルも失敗する
▶ 第2章 ステップ2
  ✖ キャンセルした人と理由を答えられる
ℹ pass 4
ℹ fail 4
```

`ℹ pass` と `ℹ fail` の行は失敗の詳細の上に出ます。画面を上に戻して確かめます。

成功した4件は、既存の業務が動いていることを示します。失敗した4件は、これから足す内容です。「キャンセルした人と理由を答えられる」が成功すれば、問い合わせに答えられます。

## 開始コードを読む

`visits.ts` の `cancelVisit` は、来院の状態を確かめて `status` を `cancelled` に更新します。このコードは、誰が、いつ、なぜキャンセルしたのかをどこにも残しません。
