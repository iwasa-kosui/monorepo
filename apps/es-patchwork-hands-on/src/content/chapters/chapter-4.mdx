## 集計テーブル

この問いに答えます。

> この集計値はなぜこの値なのか。

`daily_cancellation_counts` テーブルは、診察日ごとのキャンセル数を持ちます。テーブルの行には数しかありません。`cancelVisit` は業務イベントとキャンセル数を同じトランザクションで書きます。このパターンの開始と完成で、`cancelVisit` は同じです。開発者は読み取り関数だけを足します。

## 外部システム同期

この問いに答えます。

> 外部システムに、いつ何を送ったのか。

`cancelVisit` は来院をキャンセルしたあと、リマインダーの取り消しを外部システムへ送ります。外部への送信はトランザクションに入りません。そこで `cancelVisit` は記録を2回に分けます。

1. `cancelVisit` は、トランザクションの中で `VisitCancelled` と送信の予定 `ReminderCancellationRequested` を記録します。この記録に失敗すると、来院のキャンセルも外部への送信も行われません。
2. `cancelVisit` は、コミットの後に外部へ送り、結果を `ReminderCancellationSent` か `ReminderCancellationFailed` として記録します。

<CodeBlock code={cancelVisitOf('chapter-4-external-sync-done')} />

`chapter-4-external-sync-done` で `node what-was-sent.ts` を実行すると、次の表が出ます。時刻の値は実行のたびに変わります。

```text
┌─────────┬────────────────────────────┬────────────────────────────┬─────────────────────────────────────────────┬────────────────────────┬────────────────┬───────────────┬──────────────────────────┐
│ (index) │ requestedAt                │ finishedAt                 │ message                                     │ reason                 │ operatedBy     │ result        │ error                    │
├─────────┼────────────────────────────┼────────────────────────────┼─────────────────────────────────────────────┼────────────────────────┼────────────────┼───────────────┼──────────────────────────┤
│ 0       │ '2026-11-06T10:14:12.720Z' │ '2026-11-06T10:14:12.720Z' │ { visitId: 'visit-1', petName: 'ポチ' }     │ '飼い主の都合'         │ '受付スタッフ' │ 'sent'        │ null                     │
│ 1       │ '2026-11-06T10:14:12.720Z' │ '2026-11-06T10:14:12.720Z' │ { visitId: 'visit-2', petName: 'タマ' }     │ '来院前に回復したため' │ '院長'         │ 'failed'      │ '送信先に接続できません' │
```

## 既存の監査ログ

この問いに答えます。

> この変更の業務上の理由は何か。

`audit_logs` テーブルは、変更前後の値と操作者を持ちます。業務上の理由は持ちません。このパターンでは、監査ログと業務イベントの役割を分けます。`cancelVisit` は監査ログの ID を業務イベントの `payload` に入れます。`payload` は変更前後の値を持ちません。

<CodeBlock code={cancelVisitOf('chapter-4-audit-log-done')} />

## 持ち帰りの演習

次の手順で、選んだパターンを実装します。

1. 事前準備で展開したディレクトリの中にある、選んだパターンの開始のコードへ移動します。
2. `node --test visits.test.ts` を実行します。次の表の数が出れば、開始の状態です。
3. `visits.ts` を編集して、次の表の内容を実装します。
4. `node --test visits.test.ts` を実行します。`pass 15` と `fail 0` が出れば、実装は完了です。
5. 次の表の確認用スクリプトを実行して、問いに答えられることを確かめます。

| 開始のコード | 開始の結果 | 実装する内容 | 確認用スクリプト |
|---|---|---|---|
| `chapter-4-summary-table-start` | `pass 10`、`fail 5` | `explainCancellationCount` と `verifyCancellationCount` | `why-this-count.ts` |
| `chapter-4-external-sync-start` | `pass 11`、`fail 4` | `cancelVisit` の送信の予定と結果の記録、`findSendRecords`、`findUnconfirmedSends` | `what-was-sent.ts` |
| `chapter-4-audit-log-start` | `pass 11`、`fail 4` | `cancelVisit` の `payload` への `auditLogId` の追加、`explainChange`、`findChangesWithoutReason` | `why-changed.ts` |

解答は、名前の末尾が `-done` のディレクトリにあります。
