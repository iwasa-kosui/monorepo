## 説明

### 更新処理の中で記録する

`visits` の行には、キャンセルした人と理由がありません。`cancelVisit` の呼び出し元はこの2つを知っています。ステップ2で引数に足せるので、この演習では更新処理の中でイベントを記録します。

### 同じトランザクションに入れる

この演習では、イベントの記録を来院の更新と同じトランザクションに入れます。記録に失敗すると、来院の更新も失敗します。こうすると、記録が抜けたキャンセルは残りません。`cancelVisit` は開始時点で `withTransaction` の中にあるので、参加者はトランザクションを書き足さなくて済みます。

### business_events テーブル

`business_events` テーブルは開始時点の DB に用意してあります。

| 列 | 入れるもの |
|---|---|
| `event_id` | イベントの番号。DB が連番で採番します。 |
| `event_at` | イベントが起きた時刻 |
| `event_name` | 起きたことの名前 |
| `payload` | 操作した人や理由などの業務の情報（JSON） |
| `target_id` | イベントの対象の ID |
| `target_type` | イベントの対象の種類 |
| `target_state` | 変化後の状態（JSON） |

[関連記事](https://kosui.me/posts/2025/05/06/142842)のテーブル設計は PostgreSQL 向けで、`event_id` に UUID v7 を使います。この演習は SQLite を使い、`event_id` を連番にします。参加者の Node の下限である 24.12.0 に `crypto.randomUUIDv7` が無いためです。

## ステップ2: 理由と操作した人を記録する

同じ `cancelVisit` を、次の2か所で変更します。

1. `input` の型に `reason: string` と `operatedBy: string` を足します。
2. `payload` の `JSON.stringify({})` を、`reason` と `operatedBy` を持つオブジェクトに変えます。キーの名前はこのとおりにします。テストと第3章の SELECT は `$.reason` と `$.operatedBy` を読みます。

`node --test visits.test.ts` を実行します。`pass 8` と `fail 0` が出れば、ステップ2は完了です。
