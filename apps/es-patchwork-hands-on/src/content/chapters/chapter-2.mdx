## 説明

### 更新処理の中で記録する

`visits` の行には、キャンセルした人と理由がありません。`cancelVisit` の呼び出し元はこの2つを知っています。そこで、この演習では更新処理の中で記録を残します。

### 記録に名前を付ける

業務イベントは、業務で起きた1つの出来事を、誰が、いつ、何を、なぜとともに残す記録です。これ以降は、この記録を業務イベントと呼びます。演習で記録する業務イベントは、来院のキャンセルの1種類だけです。`visits` テーブルは、これまでどおり現在の状態を持ちます。

### 同じトランザクションに入れる

この演習では、業務イベントの記録を来院の更新と同じトランザクションに入れます。記録に失敗すると、来院の更新も失敗します。こうすると、記録が抜けたキャンセルは残りません。`cancelVisit` は開始時点で `withTransaction` の中にあるので、参加者はトランザクションを書き足さなくて済みます。

### business_events テーブル

`business_events` テーブルは開始時点の DB に用意してあります。各列は、次の問いに答えるために残します。

| 列 | 入れるもの | 残す理由 |
|---|---|---|
| `event_id` | 業務イベントの番号。DB が連番で採番します。 | 1行を指し示すため |
| `event_at` | 業務イベントが起きた時刻 | 「いつ」に答えるため |
| `event_name` | 起きたことの名前 | 「何を」に答えるため |
| `payload` | 操作した人や理由などの業務の情報（JSON） | 「誰が」「なぜ」に答えるため |
| `target_id` | 変更の対象の ID | 問い合わせの来院の記録を探すため |
| `target_type` | 変更の対象の種類 | 来院以外の対象も同じテーブルに記録するため |
| `target_state` | 変化後の状態（JSON） | その時点の状態を後から確かめるため |

[関連記事](https://kosui.me/posts/2025/05/06/142842)のテーブル設計は PostgreSQL 向けで、`event_id` に UUID v7 を使います。この演習は SQLite を使い、`event_id` を連番にします。参加者の Node の下限である 24.12.0 に `crypto.randomUUIDv7` が無いためです。

## 遅れたとき

ステップ1が終わらないうちにステップ2へ進むときは、`chapter-2-step-1` に移動して続けます。演習が終わらないうちに次の章へ進むときは、`chapter-2-step-2` に移動します。`chapter-2-step-2` は全テストが成功する完成のスナップショットです。第3章は自分のコードを使わなくても進められます。

## 足した費用を確かめる

`chapter-1-start` から `chapter-2-step-2` への `visits.ts` の変更量は、+13/-1 行です。変更した関数は `cancelVisit` だけです。`business_events` テーブルの作成は `CREATE TABLE` 1つで、9行です。`visits` テーブルは変えていません。

足した後も、次の手間が残ります。

- `business_events` の行は増え続けます。読み取りに必要な索引は、開発者が検討します。
- 記録を足す作業は、更新処理ごとに必要です。

記録には、次の限界もあります。

- 足す前の過去は分かりません。第3章で確かめます。
- 記録を通らない変更は残りません。この演習の `completeVisit` は記録しません。SQL で直接書き換えた変更も残りません。

この行数は演習の題材の数字です。自分のシステムの費用は、記録を足す更新処理の数で変わります。
